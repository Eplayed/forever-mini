# VERIFY · 倒计时口径：11-05 上午 7 点开服、天数按日历差（2026-11-03）

本轮角色：wow-dev ｜ 任务：站主问话「距离上线应该是 2 天吧，是 11 月 5 号上午 7 点开服。这次更改应该不需要小程序重新发布吧」｜ 决定原文：`PROJECT_DECISIONS.md` 2026-11-03 倒计时节

## 一、站主两条口径怎么落的

1. **目标时刻：北京 0 点 → 北京 7 点**（站主确认"是 11 月 5 号上午 7 点开服"）。
   原 0 点口径有两个实际后果都修掉：天数比真实开服少半天、且 4 号半夜倒计时整块就消失（比开服早 7 小时）。
2. **天数：整 24 小时向下取整 → 北京日历日做差**（站主："距离上线应该是 2 天"，11-03 看 11-05）。
   新读数表：11-03＝2 天、11-04＝1 天、11-05 当天没到 7 点＝「就在今天」、过 7 点＝整块消失。

**没动的**：界面那行小字（"官方公告只公布到日，具体开服时刻以游戏内为准"）原样保留——7 点不冒充官方承诺；
数据层 `meta.json` 的 launch 仍是纯日期一处真相，**OSS 数据一行不用动**。

## 二、改动文件

| 文件 | 改动 |
| --- | --- |
| `for-mini/services/countdown.js` | `launchInstant` 目标时刻加 7 小时；`state` 天数改 `bjDay(at) − bjDay(now)`（北京日历差）；头注释记站主两条原话与日期 |
| `wow-forever-web/app/src/lib/fmt.js` | `LAUNCH_AT` 00:00 → 07:00（与小程序同一个瞬间，注释互指） |
| `wow-forever-web/tools/mini-m02-check.js` | 静态卡口按新口径改写（不是删）：目标时刻断言 00:00→07:00；新增「11-03 晚 20 点看 11-05 是 2 天」固定时间戳用例；原 3 天/今天/过点三例在新算法下读数不变、断言沿用 |

m02「倒计时模块正文不许写死日期」那条闸未受影响（改动只用了 7×HOUR 这样的纯算术常量，无日期字面量）。

## 三、验证证据（静态复算，全绿）

`node --check` 两文件过；纯函数逐条断言（与 m02 静态卡口同逻辑）：

```
inst OK: true                                  ← 目标时刻 = 2026-11-05T07:00:00+08:00
before 3d4h -> d=3: true                       ← 11-02 凌晨看 11-05 是 3 天
twoDays(11-03 晚) -> d=2: true                 ← 站主原话口径
night 11-04 23点 -> d=1: true
today 11-05 早6点 -> 就在今天: true
after -> launched: true                        ← 过 7 点整块消失
no-date -> on=false: true
dayText: 11 月 5 日
web LAUNCH_AT 07:00: true | 日期段对齐 meta: true
```

`node wow-forever-web/tools/build-data.js` → **校验通过**（fmt.js 的 LAUNCH_AT 与 meta.json 对账闸含 07:00 后仍绿）。

## 四、没验到的

1. **m02 完整跑没跑**（今天 IDE 自动化链路持续不稳，与分享轮/首页轮同一原因）；倒计时那几条静态卡口已用上面的独立复算覆盖，逻辑同源。
2. 真机/模拟器里「2 天」的实拍没拍（同因）。算法是纯函数、固定时间戳验证过，上机风险低。

## 五、回答站主那句「不需要重新发布吧」

倒计时的目标时刻与算法都在**代码包**里，不在 OSS 数据里——所以这次改动**要随开发者工具上传一版代码**才能进手机
（并入今天已挂账的那次上传：分享 / 起名页 / 宏命令卡 / 首页重排同一次），**不用再发数据批次、不用为此单独提审**。
不上传的话，手机上继续是旧口径（今天显示 1 天、4 号半夜倒计时消失）。

网页端 `LAUNCH_AT` 已同步改成 7 点，但网页要**下一次发布**才带上；在那之前网页倒计时仍指 0 点（天数算法本来就是日历推进的时:分显示， vanish 时刻差 7 小时，影响小）。

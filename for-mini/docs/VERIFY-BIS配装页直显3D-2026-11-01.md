## 七、追加：相机距离自适应（站主随后要求"撑满且不失真"）

先纠一处我自己上一轮的说法。我把"画布塌小"和"相机取景"两件事混在一起报了，算完账才分得清：

| 参数 | 可见框高 = 2·d·tan(fov/2) | 高 2.0 的人占框 |
| --- | --- | --- |
| 旧（xr-frame 默认 fov≈60、d=2.4） | 2.77 | **72%** |
| 新（显式 fov=34、d 由公式算=4.09） | 2.50 | **80%** |

**所以"人只占上面一小块"的主因不是相机，是我上一轮删掉的那层 `.model` 容器**（画布退回默认小尺寸，
下面那一大片是 `.stage` 自己的底色）。容器已恢复。相机这条是顺带做的：把主体占比从 72% 调到 80%，
并把 fov 从 60 收到 34 压掉广角畸变——**不是**为了救那个塌陷。

### 做法

照网页 [ModelViewer.vue:123](../../wow-forever-web/app/src/components/ModelViewer.vue) 那条公式，只改**距离**不改比例，所以不会拉伸：

```
distance = max(高/2, 宽/(2·aspect)) × 1.25 / tan(fov/2)
```

两点与网页不同，都是被真机证据逼出来的：

1. **网页能量包围盒，小程序量不到**。three.js 有 `Box3.setFromObject`；xr-frame 在这台设备上
   连 mesh 列表都没交出来（10-30 真机回报「网格 0 个 · GLTF=true version=0」，本文件第一节引过）。
   所以小程序侧用**显式常量**代替实测尺寸：全身人形高 2.0、宽 1.0、中心 y=1.0、余量 1.25、fov 34。
2. **aspect 由页面实测**：`.stage` 是 860rpx 竖盒，但 rpx→px 每台机器不同，
   所以页面 `measureStage()` 用 `boundingClientRect` 量真实像素框算比例，再作为属性传给组件。
   量不到就传 0。

### 一条要说清的算术事实

**在我们这个框的形状范围内（aspect 0.6–1.0），算出来的距离恒等于 4.09**——高度项一直是主导项，
宽度项只有框宽到 aspect < 0.5 才会接管。所以这条"自适应"当前的实际作用是：
① 把占比固定到 80%、② 把 fov 显式写死不再依赖引擎默认值、③ 将来框改宽或换更宽的角色（牛头人）时自动接管。
**不要把它当成"竖框里变大的开关"**——真嫌人小，该调的是 `FIT` 或 `FIGURE_H`，不是这条公式。

### 安全回退（这条最重要）

组件里留着 `FALLBACK_CAM = [0, 1.2, 2.4]` / `FALLBACK_TARGET = [0, 1, 0]`，就是 10-30 真机验过的那一组。
**aspect 没量到、或算出的距离不在 0.2–60 之间 → 原样退回那组值**，宁可小也不猜一个把人裁掉。
回归脚本新加一条静态判据专门拦"把回退当冗余清掉"的下一次改动。

### 真机要看什么（我这边一条都验不了）

1. **`fov` 在 xr-frame 里到底是不是竖直视场角**。若它其实是**水平** fov，竖框下有效竖直角会小于 34°，
   人就比 80% 更大，可能**裁头或裁脚**——这是本改动唯一真正的风险点。
2. **`camera-orbit-control` 会不会覆盖我们设的 position**（轨道控制常自己维护球坐标，
   若它把距离拽回去，现象是"人还是原来那么大"）。
3. 拖动旋转后距离是否稳定；切阵营/切套重挂一次有没有闪。

组件已经把算出的数打进状态行（`modelDetail` 开头那句「画布比例 x.xx → 相机距离 x.xx（fov 34，按高 2 宽 1 估）」），
**截图里带上这一行就能一眼判方向**：若人被裁，把 `FIT` 从 1.25 上调；若人还偏小，下调 `FIT` 或改 `FIGURE_H`。

### 这一节新增的卡口

- `mini-m01-check.js` 加两条：① 页面 `stageAspect` 必须量到且 0 < aspect < 1；
  ② 组件必须留着 `FALLBACK_CAM=[0,1.2,2.4]` 且相机是 `position="{{camPos}}"` 数据绑定（不许再写死）。
- **这两条同样没在这台机器上跑过**（缺 `miniprogram-automator`），与第四节那 8 条一起在 Mac 上补。

## 八、上一节改动在真机上把画面弄没了（站主实拍，同日）

站主刷新后回报：**整格空白**，但状态行写着「画面里 18 个网格、18 张贴图（human · male）」。
这两个事实放一起就把范围缩死了——**资源与实例化都成功，是相机没拍到**。

根因：我把 `camPos` / `camTarget` 存成了 JS 数组。xr-frame 的属性走 WXML 插值，
数组会被拼成 `"0,1,4.09"`（逗号），它解析不了 → 相机掉到默认位置 → 看不见。
原写法 `position="0 1.2 2.4"` 是**空格分隔的字符串**，这是我改之前就该看见的差别。

修：常量与计算结果全部改成空格字符串（`'0 ' + cy + ' ' + dist`），
并在回归里加一条静态判据钉住"兜底值必须是字符串写法、不许出现 `camPos: [`"——
这条红过一次，值得钉。

顺带修一处我自己的话没做到的：上一节说"算出的数会随状态报出去、截图能判方向"，
实际页面 `onModelStatus` 的 ok 分支把组件传来的 `detail` **丢掉了**，只留网格与贴图数，
所以那张截图里根本没有相机数字。现在 ok 分支把 `detail` 拼回去，
下一张截图应当能看到「画布比例 x.xx → 相机距离 x.xx（fov 34，按高 2 宽 1 估）」。

`fov="34"` 这条**故意留着没回退**：它和距离是自洽的一对——
xr-frame 认这个 fov 就是约 80% 占比；不认（仍按默认 60）就是约 42%，**两种都看得见**。
所以下一张截图同时能回答第七节那个风险点：认不认 fov。
若这次仍然空白，下一个要试的是把 `fov` 属性整个去掉（回到验过的那份场景），
因为那才是"多出来的、没被证实的"变量。

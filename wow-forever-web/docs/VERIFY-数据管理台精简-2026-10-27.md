## 首页现在只回答三件事

1. **有什么急事**：物品新增待审、名录内缺详情、超过 14 天的核心板块，全部读当前 API 计算。10-27 实拍分别显示 125、612、2；第三个数只量首页七个核心板块，不把 58 份历史快照一股脑计进来。物品的 125 是 10-26 的待审快照，页面标了拉取日期，不冒充今日已重拉。
2. **哪些数据能更新**：首页七行——物品名录、世界、 副本、客户端改动、专业、传承、配装。每行只保留当前条目数、日期、来源链接与一个操作按钮。物品按钮叫“检查更新”，真实动作是按公开 API 拉到本机待审区；其余按钮叫“更新数据”，真实动作是运行现有白名单 `refresh.sh` 抓取→合并→校验，不自动发布。按钮点击本身已表达操作意图，去掉旧版多余的确认框。
3. **这次按钮做了什么**：“本次操作”只显示一句进度或差集摘要；详细 JSON 与日志折叠在“查看详细结果”。失败会显示首要错误，详细原因仍可展开。

其余九个板块放进“其他数据与更新”；原有条目检索、完整基底/上游清单、副本字段台账与三个门禁放进“高级查看”。功能仍可使用，首屏不再铺满 16 行来源表、32 份基底和全部上游快照。底部原始字段抽屉关闭时真正隐藏，不再在长截图里露出金色横线。

## 追加（2026-10-28 21:50）：工作树闸从"一堵墙"改成"先列清单、由人确认"

站主连报两次"点击更新数据被 `app/data 或 app/img 有未提交改动` 拦住"。**上一版那句"等别的会话收口工作树"
在这台机器上不成立**——多个会话同时在写 `app/data`，工作树常态是脏的，这道闸等于把按钮永久焊死。

改法（`tools/admin/jobs.py` + `server.py` + `index.html`）：

| 层 | 改了什么 |
| --- | --- |
| 判据 | 抽成 `dirty_data()`：只列 `app/data` 与 `app/img` 的未提交与未跟踪文件；`git status` 非 0 就报错，**不猜它干净** |
| 时机 | 检查移到 `start()` 里（工作线程外）。脏且未确认 → **HTTP 409 + `code:"dirty-worktree"` + 文件清单**，不建任务、不占单工作线程 |
| 界面 | 收到该码就弹确认，把会被覆盖的文件摆出来；**取消 → 页面停在"已停在检查这一步"并原样列出清单；确认 → 带 `force:true` 重发**，任务里写明"已按确认跳过工作树检查"，完成语也带这句 |
| 不做的 | 不 stash、不自动提交、不"静默改成人家点过的选择"——覆盖别人成果这一下必须是人亲手点的 |

实测（`python3 -m unittest discover -s tools/admin` **7 项全过**，新增 3 项：脏→回清单且不占线程、
确认后不带闸真跑、原有"不 force 就拒"）：

| 判据 | 结果 |
| --- | --- |
| 服务重启后不带 force 的 POST | `http=409`、`code=dirty-worktree`、`files=7`（`achievements / art / bis / talent-preview / upstream×3`） |
| 真浏览器点「更新数据」→ 取消 | 弹窗列出 7 个文件；页面 `已停在检查这一步`；**再点一次仍弹同一份清单**＝证明没起任务 |
| 真浏览器点「更新数据」→ 确认 | 拦掉真请求后抓到请求体 `{"action":"refresh","topic":"bis","force":true}`，页面继续轮询到完成语（**未真跑刷新链**，那会覆盖别的会话文件并跑十几分钟门禁） |
| 任务互斥没被绕过 | 确认前那次 409 不建任务；`已有任务运行` 仍是另一条码，不会与清单混淆 |

截图：[确认弹窗](screenshots/admin-8830-dirty-confirm-2026-10-28.png)。

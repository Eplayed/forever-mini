# 项目角色 skills 审查与候选选择

日期：2026-10-19。主角色：wow-ops。交接给：站主、Qoder。

目标来自本轮已定 D7：一个月先净赚 1,000 元，愿接定制整理、内容制作服务单。399 元报价、作者客户群仍属待验证建议，不因本次审查变为已定商业模式。

**结论：保留六角色，修正过时约束，优先补上运营角色的需求验证、报价、交付与净收入复盘。ClawHub 首选参考 Client Discovery，其次 Proposal Writing；暂不整包安装。现有 skills 更适合生产资料站，尚不足以负责首月成交。**

本轮交付是审查及可执行改造规格，未修改六份技能、未安装第三方包、未改变角色机制。技能能约束执行，不能代替真实买家、付款与履约证据。

## 2. 先处理 Qoder 能否发现技能

本机检查结果：

```text
本仓 .trae/skills/wow-*/SKILL.md：6 份
本仓 .qoder/skills/：不存在
~/.qoder/skills/：不存在
~/.qoderwork/skills/：不存在
```

Qoder IDE/CLI 官方文档列出的项目目录为 `.qoder/skills/<name>/SKILL.md`，用户目录为 `~/.qoder/skills/<name>/SKILL.md`。仅存在 `.trae/skills/`，不足以证明已经完成 Qoder 的技能注册。[Qoder IDE Skills](https://docs.qoder.com/extensions/skills)、[Qoder CLI Skills](https://docs.qoder.com/cli/Skills)（2026-10-19 查阅）。

这不代表 Qoder 绝对没读过这些文件：它可能按指令显式读取、使用导入功能或运行在另一台机器。本轮没有检查其实际会话。

建议方案：

1. 保留当前 `.trae/skills/` 六份文件作为正文唯一来源，先修正文。
2. 在项目 `.qoder/skills/` 建同名薄入口，含 `name`、`description`，正文明确要求先读取仓库中的对应 `.trae/skills/<name>/SKILL.md`，不再抄第二套完整规则。
3. 在实际 Qoder IDE 的技能列表确认六个角色出现；CLI 按官方文档重载后确认。用一次明确调用验证它确实读取正文，并在交接中记实际来源路径。
4. 薄入口如果不能可靠触发读取，再改为从唯一来源生成镜像，并用内容比对防漂移；不要人工维护两份正文。

IDE 与 CLI 文档对同名用户/项目技能的优先级表述相反，本轮不据此假定覆盖顺序；避免另装同名用户级副本，以实际加载路径为准。QoderWork 的文档另列 `~/.qoderwork/skills/`，若使用的是该产品，应按对应入口导入，不能把 IDE 的路径直接套过去。[QoderWork Skills](https://docs.qoder.com/qoderwork/skills)

上一轮派工中已经要求显式读取技能文件，Q01A 可以继续；不要把“技能目录改造”加成修 bug 的前置条件。

## 3. 六角色逐项审查

| 技能 | 合适的部分 | 具体问题 | 建议改法 |
| --- | --- | --- | --- |
| `wow-pm` | 定范围、场景、验收，职责清楚 | 仍写“宏与循环提示”共同禁做；“任何需求排在备案之后”会阻塞网页与样张；验收主要是命令和截图 | 删除复制的旧禁令，引用根规则的端别及例外；区分网页与小程序关键路径；新增买家/使用者、待验证需求、最小交付、商业假设与停止条件 |
| `wow-data` | 单一基底、来源、分歧、名称审计 | 仍一概禁 BiS 名单；未覆盖新增素材分类规则；L1 只写“官方英文”，遗漏配装线例外；部分 `docs/...` 路径缺子目录前缀 | 以根规则为权威，明确只允许的名单字段及 L1 口径；处理素材时读取最新 manifest 规则；加入“字段可用/可发布/商业交付可用”分别核对，来源存在不等于授权齐全 |
| `wow-dev` | 构建、测试、截图及“没验到的”齐全 | 新站仍写迁移中；`site-check.py` 默认与 `--app` 可选的写法已过时；没有要求关键计算独立预期；“git status 应为空”易在已有改动的工作区误判 | 新站为唯一实现对象、旧站冻结；明确新站 `--app` 门槛；计算类任务要求独立已知预期；重跑导出前后比较新增产物差异，保留已有改动，不能为了空状态清理他人文件 |
| `wow-ui` | 令牌、真实截图、移动端要求有用 | 仍描述两栈共用而未强调旧站冻结；回归命令把 `--app` 当附加项；未引用自绘副本地图就地提示的最新例外 | 只对本轮目标界面设计；最新例外读根规则，避免自行加回徽标；UI 负责视觉/交互检查，开发负责实现截图，引用同一批证据而非各拍一套 |
| `wow-planner` | 先有数据再组织内容；每块有字段映射 | 主要交付页面结构，缺少可售服务样张与查询任务结果；通常交给 UI 容易变成无条件画界面；缺口占位与最新页面留空约定存在冲突 | 增加“样张/资料交付”模式：目标任务、字段、版本、格式、免费与收费差别；不涉及视觉就直接交数据/开发或运营；空态按当前目标页面规则定 |
| `wow-ops` | 备案、主体、上线边界保留价值 | description 有增长，但正文没有获客实验、询价、报价、履约、成本与净收入；把临时账号和 OSS 地址写成常驻事实 | **优先重写**为上线、需求验证、成交交付、经营复盘四种按需模式；当前目标从 D7/经营方案读取；账号/域名从当前配置与后台证据查，不写死在 skill |

额外冲突：`wow-data` 自称唯一可改数据基底的角色，而开发流程也可能生成数据或维护发布记录。建议区分“修改采编事实/分级由数据角色负责”和“修改解析逻辑、生成产物由开发角色负责”，不能笼统地按是否处于 `src/data/` 判责；具体改动遵守根规则与本次任务授权。

这些问题的根因是同一业务规则在多个 SKILL.md 中重复维护。根规则更新后，技能副本没有同步。应把稳定的职责、输入、输出、验收放入技能，把经常变动的权限、数据例外与业务状态留给权威文档。

## 4. 首月真正需要的能力如何归属

不增加第七个“总负责人”角色，不让所有任务自动串六角色。项目协调由当前主角色按任务文件完成。

| 业务动作 | 主角色 | 必须留下的结果 |
| --- | --- | --- |
| 确认卖给谁、解决什么问题、是否值得做 | wow-pm | 真实证据与假设分开；最小交付范围和淘汰条件 |
| 准备需求访谈、记录预算和时间要求 | wow-ops | 脱敏需求记录、是否适配服务、下一步；没有买家时给招募/访谈草案，不模拟成真实反馈 |
| 把服务做成能看的样张 | wow-planner | 样张规格、明确输入输出、数据字段；必要时交数据/UI |
| 核事实与来源 | wow-data | 逐条来源、日期、版本、分歧和使用边界 |
| 给报价与限定范围 | wow-ops | 价格假设、工作范围、交付日期、修改次数、费用与退款约定；复杂规则先核实际渠道 |
| 交付可用工具或资料 | wow-dev / wow-ui 按实际需求选择 | 文件、运行/渲染证据、独立验收；不是每份表格都要开发页面 |
| 复盘是不是赚到了钱 | wow-ops | 已履约收入、退款、渠道费、新增成本、应计税费、净收入、总工时；据此继续/调价/缩范围/停止 |

技能不应把“399 元”写成永久价格，把“首月 1,000 元”写成永久目标，也不应默认作者一定是最好客户。这些从当期经营文件读取、用实际反馈修正。

## 6. 本机已有工具够不够

本机已有 skill-creator、dbs 商业工具、测试与文档类技能。它们是辅助方法，不应抢占 wow 六角色的职责。

- `skill-creator`：适合修本仓 skill 结构、触发描述与验证。本轮已用于审查原则和格式校验。
- `dbs-benchmark`：可参考其核实对标是否赚钱的思路；缺乏真实收入证据时不能把对方粉丝量当成盈利证明。其“高利润唯一标准”等绝对表述不应直接变成本项目规则。
- `dbs-diagnosis`：本轮读到多条心理归因和无来源的比例式断言。**不建议作为项目总负责人默认 skill**，避免没有销售数据就把问题归因于用户拖延或心理。
- 目标澄清、写稿、PDF、表格等能力按任务调用即可；本轮没有对它们全部做完整审计。当前目标已明确，无须再启动一轮泛化目标问诊。

## 7. 建议的 skills 改造任务书

本节可交给负责技能维护的 Qoder 会话；这是独立维护任务，不加入正在执行的 Q01A。改造仍遵循单一主角色，角色正文用 skill-creator 方法维护，不顺带执行产品开发或对外销售。

**输入**：根/子项目 AGENTS.md、六份 `.trae/skills/*/SKILL.md`、本审查、`OPS-换轨审阅-2026-10-19.md`、ROLES.md 最新决策。

**允许修改**：六份现有技能、必要的精简参考文件、Qoder 薄入口、验证文档与台账。不要改站点业务代码、数据基底、外仓内容规则或根业务红线。引用外部方法时用自己的项目化指令表述，保留来源，不整篇搬运第三方正文。

**执行顺序**：

1. S1：消除与根规则冲突的重复规定，更新新站唯一实现对象和 `--app` 验收门槛；补全相对仓库根的路径。
2. S2：扩展 wow-ops 的 description 和按需模式，明确接单、定价、样张反馈、履约、净收入复盘的触发词和产出。不把例行上线任务强行变成销售咨询。
3. S3：为 PM、策划补最小服务范围与样张模式；开发补独立预期；数据补字段用途与商业交付边界。保持职责窄，不把六个 skill 写成六份商业计划。
4. S4：补 Qoder 项目入口，验证实际发现/加载来源。正文唯一维护，不生成长期分叉副本。
5. S5：格式校验 + 以下行为验收，写 `wow-forever-web/docs/VERIFY-skills-2026-10-19.md`，然后交回独立审查。

**wow-ops 必须覆盖的最小输出契约**：

```text
任务类型：上线 / 需求验证 / 报价与交付 / 经营复盘（按任务选）
目标与约束：从当期决策读取，不写死历史目标
事实：来源、日期、真实记录；缺失写未知
假设：买家、价值、报价、渠道、时间成本
本轮动作与产出：一份能实际使用的文件或验证记录
验收：本轮用什么证据判断完成
未验证与下一步：明确负责人，不把假设记成已定
对外动作：草稿和实际发送区分，发送须有用户对应授权
```

验收场景（**本轮尚未执行，是改造后的测试要求**）：

| 输入场景 | 应观察到的行为 |
| --- | --- |
| “网页整理免费宏文本，小程序不加” | 读最新根例外并按来源与免费要求处理，不沿用旧版全面拒绝，也不扩到循环提示或付费配置 |
| “导入第三方 BiS 名单” | 核字段白名单、来源日期和 L1 口径，不复制讲解、不错误升 L0 |
| “新站配装页计算错了” | 用 app 实现和 `--app` 验收，独立预期，不编辑冻结旧站 |
| “还没有客户，想先做 399 元服务” | 给有限样张、访谈/报价草案和验证办法；不编客户、成交率或已到账收入，不强制再问已回答的目标 |
| “客户付款了，计算本月赚了多少” | 区分预收与履约、退款、费用、成本、净收入和工时，不直接把流水记为利润 |
| “小程序备案没下来，网页和样张怎么办” | 分轨判断；不把小程序备案扩大成一切动作的阻塞 |

格式通过、模拟场景通过、Qoder 实际加载成功应分开记录。不能只写一句“skills 已优化完成”。

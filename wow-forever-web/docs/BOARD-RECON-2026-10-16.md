## 二、这 15 行分三类

**已对齐（差 0）3 行**：法术书、成就、改动清单。这三行的源侧自报数是机器读得到的，
站内数也是机器读得到的，两边逐数相等；成就这一行的"页面列 198 / 数据 211"那一层
另有解释（客户端里的开发条目不列，条目没删），写在 `achievements.json` 的 `meta.counts` 里。

**有差但已解释 3 行**：稀有精英（站内是两家的并集，插件 338 + 参考站 36 − 重合 12 = 362，
脚本按 338 那把尺算差是 +24）、物品详情（差的 549 件参考站页面没有无限侧详情块，
按红线不许拿经典侧数值冒充）、副本任务（上游 407 与站内 396 不是简单加减，
合并时做过逐字重行合并、假接取人改归属、另有 29 座来自插件那份）。

**要人工核 9 行**：这一类的成因只有一种——**当年抓取时没把源侧自报数写进快照的 meta**，
所以现在只有站内一个数，没法做减法。不是漏抓，也不是数据缺失。

## 三、这 9 行怎么变成能核（下一步，不挡验收）

| 板块 | 要补的动作 |
| --- | --- |
| 物品名录 | 名称索引抓取脚本把源页自报的总数写进 `meta.counts` |
| 副本 / 首领与掉落 | 副本卡片抓取脚本把"35 座 / 每座几条首领"写进 meta；掉落那层维持待实测 |
| 专业与配方 | 专业页抓取脚本把每个专业的配方数写进 meta |
| 传承 | 那份快照只带了 build 与抓取日期，补挑战条数与专长槽位数两项自报 |
| 世界区域 | 区域表自报 43 与站内 44 的差是多列了一格城市/新区域，要在脚本里按同一颗粒度重算 |
| 天赋节点 | 源侧按"系"自报、站内按"节点"计，需要一层换算（每系几个节点）才能相减 |
| 中英术语 | 来源是官方中文稿逐句抽取，本来就没有第三方自报总数——这行按"不适用"处理 |
| 全站搜索 | 派生件，不是板块；逐类对数（数据有条数、索引必须一条不少）已经在 `build-data.js` 里拦着 |

补法都是同一件事：**让对应的抓取脚本把源侧自报数写进它自己那份快照的 meta**，
下一批按 build 重抓时顺带带上，这 9 行会自动变成可核或标出真差。

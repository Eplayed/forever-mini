# DB2 表能不能吃 · 逐条实测核对（2026-10-22）

站主让先开工 DB2 那一层。开工前不猜列序——**用一个脚本把"能不能用"的四件事量出来**：

```bash
cd wow-forever-web && python3 tools/audit-db2-item-table.py
```

脚本只读，不写任何数据文件。下面是它跑出来的结论（包 = `.scratch/wow/ziliao-export-2026-10-22/`，
客户端 build **70532**）。所有数字都是这一轮实测的，不是从上一份文档抄的。

## 一、四件事的实测结果

| 要判的事 | 实测 | 判定 |
| --- | --- | --- |
| CSV 里有没有名字 | 12 张 CSV **英文词命中全为 0** | **CSV 没解析字符串**，名字一个都不在 CSV 里 |
| FileDataID 是不是裸数值 | 拿图标表 25,078 个号反查各列：`Item.f7` 命中 **28,392 / 31,930 行** | **是裸数值**。所以"按 ID 搜不到"这种负结论是**有效证据**（上一轮那条靠这个才站得住） |
| 名字到底能不能拿回来 | 原始 `.db2` 里扫字符串块：`ItemSparse.db2` **1,725 段**（`OLDRecruit's Belt`…）、`Spell.db2` **2,758 段**（含 `${$1279976m1*$d*$<frostdamage>}` 这种描述模板）、`AreaTable.db2` **1,322 段**（`DunMorogh` / `Longshore` / `Badlands`）、`Map.db2` 50 段、`Faction.db2` 10 段 | **能拿，但要自己解析**：字符串在 `.db2` 里，导出器只把行数据转成了 CSV，没把 packed 的字符串引用还原成文本 |
| 名录差多少 | 客户端 Item 表 **31,849** 件，我们名录 **21,077** 件 | 客户端有而我们没有 **10,782 件**；我们有而客户端没有 **10 件**（见下面第三节，其中 7 件是冲突） |

## 二、这一轮真正核出来的列

| 表 | 列 | 含义 | 依据 |
| --- | --- | --- | --- |
| `Item` | `f7` | **图标的 FileDataID** | 28,392/31,930 行的值落在 `ManifestInterfaceItemIcon` 的 25,078 个号里，其余为 0（没图标）。这是"已知集合反查"，不是猜列序 |
| `CreatureDisplayInfo` | `f0`、`f8` | **疑似贴图类 FileDataID**（未定） | f0 命中 2,329、f8 命中 288。数量级不像主列，**标"待核"，不用** |
| `CreatureModelData` | `f1` | 不算发现 | 37 个命中，多半与图标号撞值。导出方自认的是 `f2=模型 FileDataID` |

沿用导出方在包内 `RESULT.json` 的 notes 里自己确认过的三条（**我没独立复验，只复述**）：
`CreatureDisplayInfo.f1 = CreatureModelID`、`CreatureDisplayInfo.f27 = 贴图变体数组`、
`CreatureModelData.f2 = 模型 .m2 的 FileDataID`。

除此之外**所有列仍是 unknown**。这张表就是"列号 → 含义 → 依据"核对表的起点，
往后每定出一列，必须像 `Item.f7` 那样带一个能复算的依据，不许凭官方列序印象填。

## 三、顺手量出来的两批名录问题（这是本轮最实际的产出）

**① 我们标"无限新增"、但客户端 70532 的 Item 表里没有的 7 件**：
`253400 真视印记`、`254380 灌魔之网`、`257029 申达尔账本`、`257127 烤泽风之种派`、
`285352 永恒探索战袍`、`285353 永恒探索者背包`、`285354 碧波尔霸`。
第三方站（wclbox）给的名单里有、编号也照抄了，客户端表里却没有；
GI 那份测试服探针（796 查不到 / 1,005 确认有）**也没查过这 7 件**，没有第三处能仲裁。
→ 已开**开放项 45**。**页面这一轮不动它们**：既不删（没依据说它们不存在，热更层是另一种可能），
也不改口径（没依据说它们一定有）。

**② 反向互相印证的 3 件**：`6216 秘法粉末`、`6374 魔化粉末`、`15754 图样：战熊热裤`——
我们标的是"无限中没有"，客户端表里确实没有。这条是好消息：**说明"无限中没有"那一格不是随手填的**。

**③ 客户端有、我们名录没有的 10,782 件**。这个数先只记着，别急着当缺口去补：
`Item` 表里明显含测试与废弃行（`Faction.db2` 里就有 "Test Faction (not a real faction)"、
`Creature.db2` 里有 "[DNT] Template Creature"），所以这 10,782 里有多少是玩家能遇到的东西，
要先把名字解析出来才分得清。**这一条再次指回同一个前置：解析 `.db2` 字符串块。**

## 四、`8119728` 那条结论的边界（说清哪些是已证、哪些还没）

- **已证**：build 70532 的 `Item` 表里，没有任何一件物品拿 `8119728` 当图标列的值。
  这条现在站得住，是因为第二节证明了 FileDataID 在 CSV 里是裸数值——搜不到才是真没有。
- **未证**：它是不是客户端里某个**别的**纹理文件的号。导出方那次是按"文件名等于 8119728"去 listfile 搜的，
  **按 ID 查 listfile 是另一回事，这一步还没做**。
- 所以 `icon-gaps.json` 里这一个键继续留着，界面继续占位块，不猜图。

## 五、要往下走，需要 Windows 侧再给三样（都很小，不用重跑大表）

1. **listfile 的 `FileDataID → 文件名` 对照**（整份或按号段切片）。有了它才能：
   把 `Item.f7` 变成能看的图标名、把 `8119728` 彻底判死或判活、
   以及**把"9 张区域底图"从"表里没有"推进到"到底是哪个文件"**。
2. **`.db2` 字符串块解析后的 CSV**（把 `*_lang` 那些 packed 引用还原成文本），
   或者告诉我们导出器用的编码规则，我们自己写解析。
   没有这一步，12 张表对我们永远只有编号，没有名字。
3. **`_cn_beta_` 那个客户端是什么**：share 根下还有一个 729 MB 的 `_cn_beta_`，
   如果它带 zhCN 数据，**官方中文名就能直接从客户端取**，不再依赖第三方站转述
   （我们现在那批 `datamine_cn` 名字全是第三方站转述的）。这条如果能成，价值比前两条加起来都大。

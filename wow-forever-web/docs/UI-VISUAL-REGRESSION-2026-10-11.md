# 视觉回归：像素基线 + 生效值指纹（wow-ui · 2026-10-11）

补的是 `docs/PLAN-open-items.md` 第 10 条欠账：**`site-check.py` 只数结构与文案，改完"像不像"没有任何东西能判**。
这条不补，改版第二批之后的每一轮都可能悄悄走样——历史上已经走过好几次（媒体查询被后面的基础规则盖掉、
新组件类名与「来源轨」撞名把左轨压掉、导航加一项就换行成两行）。那些都是人眼在截图里发现的，机器当时全绿。

工具：`wow-forever-web/tools/visual-check.py`。两层判据，各管一类毛病。

## 一、两层判据分别抓什么（都是实测，不是推测）

| 层 | 判据 | 抓得住 | 抓不住 |
| --- | --- | --- | --- |
| 像素 | ①整页尺寸必须一致 ②变化像素占比 ≤0.4%（单像素色差 >24 才计数） ③平均色差 MAD ≤0.35 | 布局错位、块被压掉、整页染色漂移、页面变长变短 | 只动几个像素的小改动 |
| 生效值指纹 | 每页每视口读 121 个**实际生效**的样式值（24 个令牌 + body/H1/H2/卡片/导航当前项/链接/控件/来源轨/L0–L3 徽标），逐键比对 | 令牌被改回去、圆角回到大圆角、字体换回系统、分级徽标颜色并色、品牌色复活 | 值没变但层叠把样式盖没了（那种归像素层） |

四个实测对照，说明为什么必须两层：

1. **同一版本取两次图** → 32 张全 0.00%、占比与 MAD 都是 0.00，指纹 121 键全一致。工具本身不带噪音，
   这是后面所有结论的前提。
2. **只把 `--bg` 从 `#101010` 改成 `#161616`**（一步灰阶，人眼几乎看不出）→ 像素占比 0.00%（**漏**），
   MAD 1.92（**挂**）。所以占比之外必须留 MAD 这个判据。
3. **只把 `.card` 圆角从 3px 改成 8px** → 像素层 0.00% / 0.00 全过（**两层像素判据都漏**），
   指纹层直接点名 `card.borderRadius 3px → 8px`。而"2–3px 硬边"正是 2026-10-11 定下的改版决策之一——
   这种"决策被改回去却悄无声息"的回归，只有比生效值才抓得住，这也是加第二层的唯一原因。
4. **给 `.card` 加 30px 下边距** → 尺寸判据立刻挂：`基线 720x2653 → 本次 720x2674`。

## 二、命令

```bash
python3 tools/visual-check.py --make                    # 冻结当前版本：像素基线（本机）+ 指纹（入库）
python3 tools/visual-check.py --check                   # 改版后跑：两层都比，非 0 即回归
python3 tools/visual-check.py --check --only-fingerprint  # 只比生效值：80 秒，跨机器可用
python3 tools/visual-check.py --check --only dungeons --src ../src   # 调试单页
```

接在改版验收链的哪一步：`build-data.js` → `site-check.py` → `app-parity.py` → **`visual-check.py --check`**
→ 人眼过一遍截图 → 认可了新外观才 `--make` 重冻。顺序反了就等于把半成品冻成标准。

## 三、三条让结果可信的做法（不看代码的话容易被忽略）

1. **取图默认从 git 版本取，不从工作区取**。`--rev`（默认 HEAD）用 `git archive` 把那份 `src` 解到 /tmp 再开服务。
   理由很实际：写这个工具的同时，另一个会话正在改 `src/js/app.js` 与 `src/css/app.css`；
   直接拿工作区取图，就会把别人改到一半的页面冻成"标准答案"。要比正在改的版本请显式 `--rev WORKTREE`。
2. **拍之前把会变的东西按死**：清掉所有定时器，把倒计时三处节点（`#lchip` / `#cdD` / `#cdT`）写成等宽占位文字，
   关掉全部动画与过渡，懒加载图强制 eager 并等 `document.images` 齐、`document.fonts.ready`。
   不归一的话同一份代码两次截图都对不上，工具就成了噪音机——上面实测 0.00% 就是这套归一的结果。
3. **像素基线不进仓库，指纹进仓库**（`docs/visual-fingerprint.json`，130 KB，32 页 × 121 键）。
   像素基线 16 页 × 两视口降采样后仍要 18 MB，PNG 在 git 里压不动，每重冻一轮永久多留一份；
   更关键的是它只有"同一台机 + 同一个 Chrome + 同一套本地字体"才可比，存进仓库等于给别人存一份必然全红的假标准。
   要复现：`--make --rev <提交号>`。指纹是文本，跨机器可比，所以它进仓库。

## 四、它管不了什么（别把它当万能闸）

- **数据与文案变了也一定红**：页面文本变了像素就变了。这不是回归，是"该重冻"——先看差异图确认是内容变化，
  再 `--make`。所以重冻必须是人工动作，不能塞进自动链。
- **不做与参考站的像素比对**。诊断稿里提过"每页与 `docs/reference/` 基线做像素 diff"，这条路我否了：
  我们的页面内容和 Wowhead 不同，像素 diff 只会得到"整页都不同"，没有判据意义；
  而且第三方站图片不入库（红线）。"像不像那个站"仍然是人眼判断，工具只保证**别从已定稿的样子走样**。
- 不管性能、无障碍、移动端命中区（`site-check.py` 第 6 节那套量化判据管）。
- 部分页跑（`--only`）时，指纹里其余页会报"（整页）基线 有 → 本次 缺"，那是范围不对，不是回归；全量跑就没这行。

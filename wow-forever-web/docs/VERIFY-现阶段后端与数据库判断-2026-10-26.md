# 现阶段后端与数据库判断（2026-10-26）

本轮角色：wow-dev。范围：只读核对当前仓库的网页、小程序与 OSS 数据链，判断目前是否需要新增运行时后端和数据库。没有修改代码、数据、OSS 对象或线上配置。

## 结论

**目前不需要为资料站或小程序另建运行时后端与数据库。** 当前核心功能是公开资料查询：项目本地维护一份 `wow-forever-web/app/data/` 数据基底，构建后发布静态 JSON 与图片；客户端读取、搜索、筛选和本地缓存。OSS 是小程序的数据分发与版本回滚层，不能把它称为关系数据库，但对这阶段的公开只读资料足够。

需纠正一个前提：按本地当前代码，**小程序直接请求 OSS；网页没有直接请求 OSS**。网页 `app/src/lib/data.js` 用 `fetch(assetUrl(file))` 读取站点相对路径；`tools/app-assets.py` 把 `app/data/` 同步到 `app/public/data/`，构建后随静态站发布。`app/vite.config.js` 的相对 `base` 也服务于这条站点内资源路径。部署脚本 `tools/deploy-gh-pages.py` 当前指向 GitHub Pages 静态产物。网页以后可以改为 OSS/CDN 分发，但无需因此上后端或数据库；上线实际地址应另以部署状态核实。

小程序 `for-mini/services/oss-manifest.js` 目前指定 `ACTIVE_ENV='beta'`，通过 OSS 的 `wow/{env}/v1/manifest.json` 指针定位不可变批次，再按索引／详情／掉落分片加载。`for-mini/services/forever-data.js` 统一调用它，并提供本地缓存、部分打包快照；页面须显示 `live/cache/snapshot/none` 的真实状态。`tools/oss-release.js` 负责构建批次、校验、上传、最后切换指针和回滚。代码指向 beta 不等于已经证明正式线上批次可用，发版仍需单独验收。

## 现在怎样维护数据

`app/data/` 是唯一可编辑的数据真源；改动先通过 `tools/build-data.js`。网页重新构建并发布静态站时带上 JSON 副本；小程序由 `tools/export-mini.js` 与 `tools/oss-release.js` 生成和发布 OSS 批次。两条发布链可分别执行，**更新本地真源本身不会自动更新网页或 OSS**；需要记住两端当前发布的版本、核对日期与回滚批次。图片同样按本地素材和发布清单分发。

当前适合继续放在客户端的状态：收藏、最近查看、筛选条件、无需跨设备同步的临时配置；现有收藏用小程序本地 storage，网页方案分享可用 URL hash。公开查询、章节文章、免费只读宏／WA 条目、插件名单和自写公告整理都可以先用版本化 JSON/静态页面承载，不以新增数据库为前置条件。数据量或访问量增长时，先量首屏字节、请求数和命中情况，再考虑分片、缓存或 CDN；增长本身不自动要求数据库。

## 何时再考虑后端或数据库

| 出现的真实需求 | 需要解决什么 | 建议的最小升级 |
| --- | --- | --- |
| 要把表单、预约或装配服务工单**自动收集并跨设备管理** | 可信写入、去重、状态和隐私保护 | 先明确业务和主体边界，再做受控表单接口＋小型持久化存储；人工联系与人工台账阶段可暂缓 |
| 要让用户登录、跨设备同步个人配置或服务记录 | 身份、授权、数据隔离 | 需要服务端身份与存储；这与当前项目“小程序不做登录”的规则冲突，先由产品角色改范围 |
| 要处理订单、收费、私有素材或受保护的密钥／AI 调用 | 服务端校验、权限、账务或密钥保护 | 必须引入服务端能力及相应存储；当前小程序禁止虚拟支付，免费宏／WA／配置也不能做成付费品 |
| 有高频实时数据或大量关联条件查询，静态快照已无法按期更新或客户端查询明显吃力 | 增量更新、查询计算和一致性 | 先拿更新时延、文件规模和查询性能证据，再评估 API 与数据库；不要预先迁移全部资料 |

如果将来出现以上一项，也只为那项新增最小服务，不把所有公开资料都搬进数据库。静态资料继续走现有基底、构建校验和版本化分发，避免网页与小程序再出现第二份事实真源。

## 边界与未验项

- **已定（代码核查结论）**：目前公开只读资料不用新增运行时后端或数据库；小程序 OSS 直读，网页静态站内 JSON 直读。
- **待核**：本轮未调用线上网址或 OSS 做真实网络回读，不能据此宣称当前 release 指针、合法域名、CORS、真机请求或两端线上版本已通过。若下一步是正式发布，按各自发布验证记录核实。
- **交接给站主**：继续使用当前静态架构；先量实际使用和更新成本。只有明确要收集、同步、保护或实时处理的数据时，再单独立后端需求。

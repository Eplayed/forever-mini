## 四、`Item` / `ItemSparse` 里没有模型号——这条是证死的，不是猜的

用第二节的 34,726 个模型号做"已知集合反查"（和当初定 `Item.f7 = 图标号` 同一个办法，
那次命中 28,392/31,930 行才算定住）：

| 表 | 列 | 数值行 | 命中模型号 | 判定 |
| --- | --- | --- | --- | --- |
| `Item` | 除 id 外全部 16 列 | — | **0** | 没有模型列 |
| `ItemSparse` | `f22`–`f26` | 19,320 | 最高 12 行（**0.06%**） | 噪声；这几列的值是打包浮点（如 `1065353216` = 1.0f），不是编号 |
| `ItemSparse` | `id` | 19,320 | 54（0.28%） | 纯号段重叠，不是引用 |

**所以：装备→模型这一跳必须走 `ItemDisplayInfo.db2`**（经典那套布局里它的 `FileDataID` 就是模型本体），
而这张表**还没被导出过**——本地和共享上那份 `db2/` 都只有 12 张表，不含它。

## 五、我卡在哪：最后两跳都要在那台 Windows 上做

1. **取 `.db2` 与 `.m2` 要执行 Windows 侧的工具**。这台 Mac 探过：`22`(SSH)、`5985`(WinRM)、`3389` 都不通，
   只有 `445/139`(SMB) 开；`C$` 用 `share` 账号挂不进去（不是管理员），所以**我无法远程执行**。
   CASC 那套解码（encoding key → ENCODING → .idx/.cnt → BLTE 分块解密 + sparse 解压）
   就是 `wowfexport` 干的事，我不会为这一个素材重写一遍客户端解包器。
2. **`.m2` → `.glb` 的转换器是图形界面**（`Kruithne/wow.export`，能导 OBJ/GLTF、支持 Classic、可拖本地 M2/BLP），
   没有命令行 → 就算把 .m2 取回来，38 套要能重烘还得单独解决批量这一步（这是工时，不是红线）。

### 4.5 同日补查：可能整条"烘 GLB"都不用做（`three-m2loader`）

上面那句"要么烘 GLB、要么自研"是个假两难，我搜漏了第三条路。实测查到的（都是现读源码，不是印象）：

| 候选 | 结论 |
| --- | --- |
| npm `wow-models` 1.1.1 | **同名占坑，无关**（3.2 KB、依赖 mongoose/bcrypt）。别引用 |
| `barncastle/wow-mdx-viewer`（MIT/TS） | **不适用**：README 明写只支持 0.11.0.3925 之前、MDX v1300/1400/1500，且读 MPQ；我们是 CASC + 新版 M2 |
| **`Mugen87/three-m2loader`**（MIT，npm 5.2.0，最后提交 2024-08） | **可用候选**：浏览器里直接解析 M2（MD20/MD21 块），版本常量覆盖 256 Classic / 263 TBC / 264 WotLK / 274 Legion（BfA 与暗影界同号），正好是我们这种经典底分支的区间；`.skin`/`.blp` 按 FileDataID 或文件名同级放置即可解析 |

**但它有两个限制要如实记**：① 源码里 `attachment` 命中 **0 次** → 它只渲染单个 M2，**不负责把"身体 + 16 件装备"拼成一个角色**；
② 它 pin 的是 `three@0.159.0`，我们站上是 0.186.1，接进来要先解这个版本差。
所以路线变成：**烘 GLB 不再是唯一选项**——"浏览器端加载 body.m2 + 各部位 .m2、我们自己往骨骼上挂"这条路的
工作量是应用层胶水，不是自研 M2 解析器。而这条路能不能成，仍取决于同一件事：
**本 build 缺 `CharSections`/`PlayerKit`，身体与皮肤那一层到底怎么定**（见第五节，要 Windows 那 9 张表判）。

**要在那台 Windows 上跑的（2026-10-26 与对面 AI 对齐后的最终口径，共两步）**：

第一步 · 导 9 张表（fdid 已逐张在 listfile 核过，总量约 6.5 MB；其余 78 张一张都不碰）：
`ItemDisplayInfo` 1266429、`ModelFileData` 1337833、`ItemDisplayInfoModelMatRes` 4050937、
`ItemAppearance` 982462、`ItemModifiedAppearance` 982457、`ItemModifiedAppearanceExtra`、
`ComponentModelFileData` 1349053、`ComponentTextureFileData` 1278239、`TextureFileData`。
每条出 `.db2` + `schema.json` + CSV。列序一律用"已知集合反查"定（模型号集 S = 34,726 个
`ITEM/`+`CHARACTER/` 下的 `.m2`；另备 `.skin` 与 `.blp` 号集），每条候选列要报命中数/总行数与 3 个可复核样例，
达不到结论就写"未定"。两条链都要判：A 物品侧 `ItemSparse → ItemDisplayInfo →(FileDataID/ModelFileDataID)→ ModelFileData`，
B 组件侧 `ItemModifiedAppearance → ItemAppearance → ComponentModelFileData`。
**停手线**：拿本站 177 件装备实跑覆盖率，≥80% 就停手报数等我，<80% 就报断在哪一跳——两种情况都不许继续扩表、不许开始写转换器。

第二步 · 取一件装备的**完整素材闭包**（`.m2` + `.skin` + `ModelFileData` 指到的全部 `.blp`，按原相对路径，<10 MB），
先挑战士 PvE 联盟那套里的胸甲 1488 与主手 280604。取回来我在这边直接用 `three-m2loader` 在浏览器里试渲染，
**成了就不需要烘 GLB、也不需要自研任何解析器**；烘 GLB 只作为它渲染不出来时的备选。

## 六、这三条跑通之后会发生什么

- 我把 `ItemDisplayInfo` 的模型列用同一套反查定死（拿 34,726 个模型号当已知集合），
  然后 **`bis.json` 的 177 件装备 → 各自 `.m2` 号 → 路径 → 取文件**，这条链就能算出来。
- 真模型进 `app/img/models/`，`origin` 从 `self-generated` 改成 `client-export`，
  `register-bis-models.py` 那道"非自产拒收"的闸要跟着改口径——**这一步要站主先点头**：
  游戏客户端的模型烘成 GLB 放进公开静态托管，比现在那几张客户端原画硬一档（待办 #104）。
- 烘 38 套要能自动化，还得解决转换器无 CLI 那条（可以只做人工烘一批、或自己写脚本走它内核）。
  **2026-10-26 补**：这条可能整个绕开——见 4.5 节，`three-m2loader` 若能在浏览器里解析我们的 M2，
  就不需要离线烘 GLB，代价变成"要不要把游戏模型文件直接下发到浏览器"（红线口径另说）。

## 四、`Item` / `ItemSparse` 里没有模型号——这条是证死的，不是猜的

用第二节的 34,726 个模型号做"已知集合反查"（和当初定 `Item.f7 = 图标号` 同一个办法，
那次命中 28,392/31,930 行才算定住）：

| 表 | 列 | 数值行 | 命中模型号 | 判定 |
| --- | --- | --- | --- | --- |
| `Item` | 除 id 外全部 16 列 | — | **0** | 没有模型列 |
| `ItemSparse` | `f22`–`f26` | 19,320 | 最高 12 行（**0.06%**） | 噪声；这几列的值是打包浮点（如 `1065353216` = 1.0f），不是编号 |
| `ItemSparse` | `id` | 19,320 | 54（0.28%） | 纯号段重叠，不是引用 |

**所以：装备→模型这一跳必须走 `ItemDisplayInfo.db2`**（经典那套布局里它的 `FileDataID` 就是模型本体），
而这张表**还没被导出过**——本地和共享上那份 `db2/` 都只有 12 张表，不含它。

2. **`.m2` → `.glb` 的转换器是图形界面**（`Kruithne/wow.export`，能导 OBJ/GLTF、支持 Classic、可拖本地 M2/BLP），
   没有命令行 → 就算把 .m2 取回来，38 套要能重烘还得单独解决批量这一步（这是工时，不是红线）。

### 4.5 同日补查：可能整条"烘 GLB"都不用做（`three-m2loader`）

上面那句"要么烘 GLB、要么自研"是个假两难，我搜漏了第三条路。实测查到的（都是现读源码，不是印象）：

| 候选 | 结论 |
| --- | --- |
| npm `wow-models` 1.1.1 | **同名占坑，无关**（3.2 KB、依赖 mongoose/bcrypt）。别引用 |
| `barncastle/wow-mdx-viewer`（MIT/TS） | **不适用**：README 明写只支持 0.11.0.3925 之前、MDX v1300/1400/1500，且读 MPQ；我们是 CASC + 新版 M2 |
| **`Mugen87/three-m2loader`**（MIT，npm 5.2.0，最后提交 2024-08） | **可用候选**：浏览器里直接解析 M2（MD20/MD21 块），版本常量覆盖 256 Classic / 263 TBC / 264 WotLK / 274 Legion（BfA 与暗影界同号），正好是我们这种经典底分支的区间；`.skin`/`.blp` 按 FileDataID 或文件名同级放置即可解析 |

**但它有两个限制要如实记**：① 源码里 `attachment` 命中 **0 次** → 它只渲染单个 M2，**不负责把"身体 + 16 件装备"拼成一个角色**；
② 它 pin 的是 `three@0.159.0`，我们站上是 0.186.1，接进来要先解这个版本差。
所以路线变成：**烘 GLB 不再是唯一选项**——"浏览器端加载 body.m2 + 各部位 .m2、我们自己往骨骼上挂"这条路的
工作量是应用层胶水，不是自研 M2 解析器。而这条路能不能成，仍取决于同一件事：
**本 build 缺 `CharSections`/`PlayerKit`，身体与皮肤那一层到底怎么定**（见第五节，要 Windows 那 9 张表判）。

**要在那台 Windows 上跑的（2026-10-26 与对面 AI 对齐后的最终口径，共两步）**：

第一步 · 导 9 张表（fdid 已逐张在 listfile 核过，总量约 6.5 MB；其余 78 张一张都不碰）：
`ItemDisplayInfo` 1266429、`ModelFileData` 1337833、`ItemDisplayInfoModelMatRes` 4050937、
`ItemAppearance` 982462、`ItemModifiedAppearance` 982457、`ItemModifiedAppearanceExtra`、
`ComponentModelFileData` 1349053、`ComponentTextureFileData` 1278239、`TextureFileData`。
每条出 `.db2` + `schema.json` + CSV。列序一律用"已知集合反查"定（模型号集 S = 34,726 个
`ITEM/`+`CHARACTER/` 下的 `.m2`；另备 `.skin` 与 `.blp` 号集），每条候选列要报命中数/总行数与 3 个可复核样例，
达不到结论就写"未定"。两条链都要判：A 物品侧 `ItemSparse → ItemDisplayInfo →(FileDataID/ModelFileDataID)→ ModelFileData`，
B 组件侧 `ItemModifiedAppearance → ItemAppearance → ComponentModelFileData`。
**停手线**：拿本站 177 件装备实跑覆盖率，≥80% 就停手报数等我，<80% 就报断在哪一跳——两种情况都不许继续扩表、不许开始写转换器。

第二步 · 取一件装备的**完整素材闭包**（`.m2` + `.skin` + `ModelFileData` 指到的全部 `.blp`，按原相对路径，<10 MB），
先挑战士 PvE 联盟那套里的胸甲 1488 与主手 280604。取回来我在这边直接用 `three-m2loader` 在浏览器里试渲染，
**成了就不需要烘 GLB、也不需要自研任何解析器**；烘 GLB 只作为它渲染不出来时的备选。

## 九、round-3 验收与对面复算（同日追加）

对面 AI 第三轮交回来两件真事 + 一处它自己查出的缺陷，我逐条独立复算，不采信转述。

**交付完整性**：manifest 70 条逐条回读，`bytes` 与 `sha256` **70/70 全对**，manifest 不再含自身条目
（上一轮那两处自指不符已修）。9 张表这次三份齐全。

**它自查出的解码缺陷是真的，而且比漏交更严重**：`db2csv3.field()` 对 stype 4（数组列）按 `addsize/4`
整块展开，把整段调色板塞进一个单元格——`ItemDisplayInfo.csv` 曾 27.7 MB、最长单元格 26,894 字符。
修正后 569,082 字节、最长单元格 10 字符，列变成 `f10.l0`/`f10.l1` 这种分道写法。

**我对面的复算**（用它的原始 CSV 自己接链，不读它那份 `item-to-model-fdid.csv`）：

| 跳 | 命中 |
| --- | --- |
| `ItemModifiedAppearance.f3 → ItemAppearance.ID` | 99.99% |
| `ItemAppearance.f1 → ItemDisplayInfo.ID` | **47.14%** ← 断点就在这 |
| `ItemDisplayInfo.f10.l0 → ModelFileData 分组 id` | 98.08%（`f10.l1` 96.67%、`f11.l0` 77.69%、`f11.l1` 81.93%） |

**本站 177 件配装装备的覆盖率，复算结果与它给的数完全一致**：
58/177 件 = **32.8%**；纸娃娃格位 352/1261 = **27.9%**；**看得见的部位 352/845 = 41.7%**；
76 个角色（38 套 × 两阵营）里可见部位能穿满的 **0 个**。
分部位：肩/主手/远程 100%、副手 97.8%、头 81.6%、背 71.1%，
**胸·腕·手·腰·腿·脚 = 0%**，戒指/饰品/项链/圣物 = 0%（这几类本来也不上身）。
0% 的那六类不是"没查到"：能解析出模型的路径 100% 落在 `Item/ObjectComponents/{Head,Shoulder,Weapon,Shield}`，
身体护甲在本 build 的这批表里**没有独立模型登记**。

**它的负结论我独立验到同一结果**：`ItemDisplayInfoModelMatRes` 不含"材质→贴图"关系——
`f0` 落在 `TextureFileData.ID` 只有 1.47%（随机基线 5.45%，比随机还低），
落在 `file_fdid` 0.79%；它倒是命中 `ModelFileData.group_id` 77.57% 与 `ItemModifiedAppearance.ID` 73.13%，
所以 f0 是模型/外观侧的键，不是贴图号。**"每件装备用哪些 .blp"在这 9 张表里确实没登记。**

**我自己两次差点报错的账，记下来**：① 第一次复算跑出 0%，是我把 `ext` 列按 `.m2` 过滤（实际值是 `m2` 不带点）；
② 验 `f0` 时我按 `id` 取列（实际列名是 `ID`），拿到一个假的 0.00%。两次都是判据写错，不是数据坏——
**负结论出 0 的时候先怀疑自己的脚本**。

## 十一、C 路线开挖（同日，站主选 C）

先判"值不值得写解析器"，用已交付的数据 + 共享上的 listfile 做文件层探查。
（那台 Windows 当晚 23:4x 起 ping 不通，listfile 用不了；下面的文件层结论改用交付的
`modelfiledata-group-to-files.csv`（121,131 行带路径）与 `texture-filedata.csv`（58,693 行带路径）得出。）

**① 身体护甲确实没有独立模型文件**——模型注册表里 `Item/ObjectComponents/` 下的全部子目录只有：
`Head 23,512`、`collections 8,097`、`Shoulder 2,152`、`Weapon 653`、`Shield 61`、`Ammo 6`、`cape 4`、`Waist 2`、
`Quiver 1`、`backpack 1`、`Scroll 1`——**没有 Chest/Legs/Feet/Hands/Wrist 任何一类**。
所以"身体那六件"不是没查到，是这个 build 里就没有对应的模型资产。

**② 但身体贴图的骨架在，而且是 8 槽位制**：`Item/TextureComponents/{TorsoUpper,TorsoLower,LegUpper,LegLower,
ArmUpper,ArmLower,Hand,Foot}Texture/` 共 **12,995 张**（另 `Character/<种族>/<性别>/` 下 1,000+ 张皮肤贴图），
身体模型本身也在：`Character/<种族>/<性别>/<种族><性别>.m2` 共 **143 个**。
⇒ 身体护甲 = 身体模型 + 8 个槽位各贴哪张图，这套资源是齐的，缺的只是"哪件装备用哪几张"的索引。

**③ 索引字段找到了，但本 build 里几乎是空的**：`ItemAppearance.f4` 的两个非零值 `163903/163904`
**100% 落在 `TextureFileData` 的贴图号值域（117401–176093）**——这一列就是"装备→身体贴图"的入口。
问题是：9,059 个外观里只有 **248 个（2.7%）** 填了 f4，我们 177 件里 149 件有外观记录、
其中只有 **2 件** 有 f4。同一张表里 `f1`（→ `ItemDisplayInfo` 行）也只有 47.14% 能落进本 build 的 7,071 行 IDI。
⇒ **不是我们解错了列，是这个客户端把外观数据裁掉了**：表结构完整、数据近乎空。

**④ 其余列排除**：`f2`（115 个去重值，132405–443367）不落在贴图号也不落在模型分组（0%），
按对面判读是图标；`f3` 值形如 `ID×100`（样例 2352 → 235200）是打包派生值；`f0` 12 个值 1–15 是枚举。

## 十二、C 还差一次导出就能判死/判活

`TextureFileData` 与 8 槽位贴图都在，缺的是"物品 → 槽位贴图"的索引表。本 build 里没被排除的候选还剩五张：
`CharComponentTextureLayouts`、`CharComponentTextureSections`、`HelmetGeosetData`、`ConditionalItemAppearance`、
`ItemModifiedAppearanceExtra`（前三张在 listfile 里已确认存在）。
其中 `CharComponentTextureSections` 在零售端就是"每个槽位用哪张贴图 FileDataID"的登记表——
**如果它在本 build 里也带着贴图号，C 就活；如果它也是空表或不含贴图号，C 判死，转 B（只做单件预览）。**

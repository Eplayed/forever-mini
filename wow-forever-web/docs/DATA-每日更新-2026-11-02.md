# 每日数据更新 · 这台 Windows 的入口（2026-11-02）

站主 2026-11-02 定：**Mac 那边不再做，全部在这台 Windows**；每天开机手动跑一次数据更新，保证数据准确。
这一篇是那一台机器上"每天要敲的那一条命令"的说明，以及为了把它跑通今天修掉了什么。

## 一、每天就跑这一条

```bash
cd /d/project/forever/wow-forever-web
bash tools/daily.sh
```

实测 **17~22 分钟**（11-02 那一次逐步相加约 17 分钟，大头：`⑤ 门禁` 560 秒，其中 site-check 单跑约 9 分钟；
`③` 里最慢的是 dungeons 140s、quests 118s、talents 68s、items 72s）。
跑完在终端打 5 行摘要，详细报告落 `docs/DATA-每日体检-YYYY-MM-DD.md`；
**有步骤红的时候临时目录不删**，终端会打印每一步的全程输出在哪，直接去读那一个文件。

两个调试用的形态：

| 命令 | 用途 |
| --- | --- |
| `bash tools/daily.sh --quick` | 只跑探源 + 插件层 + 并成品 + 门禁，不重抓网页那八块（改了抽取器时用它） |
| `bash tools/daily.sh --no-gate` | 只抓到并完，界面回归留到之后（急着出数据时用，发版前必须补跑 `refresh.sh check`） |

链条顺序写死在这里，别再靠人脑记：

```
① 探源 daily-probe.py        必需来源不通 → 整条停，旧快照日期不动（必需源允许重试一次，可选源不通只记录）
② 插件层抽取 refresh.sh addons   GI / XR / DF 十三个抽取器，只写 upstream 快照
③ 各板块重抓 refresh.sh world|changes|dungeons|prof|legacy|talents|official|quests|items|icons
                              每一遍带 WOW_SKIP_GATE=1，不重复跑门禁
④ 插件并成品 refresh.sh addons-merge   必须排在 ③ 之后（见下）
⑤ 统一门禁 refresh.sh check   数据卡口 + 译名逐字回查 + 构建 + 单测 + 界面回归，跑一次
⑥ 报告 daily-report.py
```

**为什么 ③ 每步跳过门禁**：十个场景各跑一遍完整门禁 = `site-check` 跑十遍（单跑约 12 分钟）。
`WOW_SKIP_GATE=1` 只是把重复去掉，门禁本身一道没减——⑤ 统一跑一次。

**③ 里的顺序是有条件的**：`quests` 吃 ② 抽出来的 GI 任务快照、`items` 吃 GI 的存在性探针，
所以必须在 ② 之后；`icons` 放最后，让前面新写进去的 `iconKey` 先进 `build-icon-map` 的登记表再补图。

**为什么 ④ 必须排在 ③ 之后**：`merge-dungeons.js` / `merge-professions.js` 是整表重写，
插件并进去的字段先写就会被冲掉。专业线已经栽过一次（`refresh.sh` 的 prof 注释）。

## 七、数据工作台（Mac 上做的那套）在这台的现状

站主让"从 Mac 找到数据工作台并拷过来"。**结论：不用拷——两边逐文件 git blob 哈希完全相同**，
`wow-forever-web/tools/admin/`（`server.py` / `catalog.py` / `jobs.py` / `index.html` / `test_admin.py`）
本机 11-01 就已经带着了；Mac 那边该目录 `git status` 干净、只有一个未跟踪的 `review/`（是本地产物，`.gitignore` 已挡）。
真正的问题是**它在 Windows 上跑不起来**，今天就着测出来的一批一起修了：

| 毛病 | 症状（实测） | 修法 |
| --- | --- | --- |
| `subprocess(text=True)` 按 GBK 解码 | bash 一输出中文，读取线程就抛 `UnicodeDecodeError`，`git status`/`refresh.sh` 的输出会整段丢 | 7 处全部补 `encoding="utf-8", errors="replace"`（`server.py` 里本来就有正确写法，照它对齐） |
| 跨盘 `os.path.relpath` | `test_scan_items` 直接崩：`path is on mount 'C:', start on mount 'D:'` | 加 `_ref()`：跨盘退回绝对路径，不让整条任务崩 |
| 刷新链超时 900s | 这台 `site-check` 单跑约 13 分钟，900s 会把快跑完的链当卡死杀掉 | 提到 2700s，注释写了实测时间 |
| 宏板块指向空字段 | 控制台"宏条目"显示 **0**，而真源 `macros.json` 有 245 条（`guide.json.macros` 至今是 0） | 新增 `macros` 板块指向 `macros.json`；`guide` 改回"插件目录"只管 addons；缺口卡也改读 `macros.json` |
| 宠物标"未建库" | 其实 `pets.json` 11-02 就有 18 家族 / 22 技能，页面进不去 | 板块接上，条数显示 40（家族+技能） |
| 天赋数与卡口打架 | 页面 **508**、`build-data.js` **466**——因为它把 `_demo.json` 的 42 个演示节点也数进来、还能浏览 | 与卡口同口径跳过 `_` 开头文件，两边现在都是 466 |

**验证方式不是"我改了"**：`python3 -m unittest discover -s tools/admin -t tools/admin` → **8/8 OK**；
再把服务真起起来打接口 → 17 个板块、物品 21,296 / 宏 245 / 宠物 40 / 天赋 466，缺口卡"宏条目"从 0 变 245。
（我第一版探测脚本把 `/api/catalog` 读成 0 个板块、把 `/api/review/items` 的 404 当成故障——
前者是我没看返回键叫 `topics`，后者是它设计好的"尚无待审快照"，两条都是我脚本的错，不是服务的。）

启动：`cd wow-forever-web && python3 tools/admin/server.py`（默认 `127.0.0.1:8830`，只认本机主机名）。
它的 `refresh` 动作**跑前会自动把 `app/data`/`app/img` 的未提交改动收口成一次本地提交**（pathspec 只碰这两个目录，
不会卷走别的线 staged 的文件），跑完再提交一次产物，**不 push、不发布**——这条设计正好合这台"多会话同工作树"的现状。

还接不上的一条：`scan_items` 走 wclbox 公开 API（今天实测 200 活着），但它落的 `review/` 是本地待审区，
**不并成品**；物品线的「一键刷新」本轮补上了（`refresh.sh` 新增 `items` 与 `quests` 两条场景，
`catalog.py` 的 workflow 列同步填好，工作台现在 **9 个板块**带按钮：items / world / changes / dungeons /
dungeon-quests / professions / legacy / talents / bis）。插件层 `addons` 场景仍**没做成按钮**——
它跑十三个抽取器、只写 upstream 不动成品，按钮文案要说清"这只刷新一半"，接法等站主定，不拿"刷新"当幌子。

## 十、站主要的那两件事：本地 vs 线上对账 + 一个按钮（方案，待确认）

站主 11-02 追问："能不能一眼看出我们和线上的数据库版本需不需要更新，在数据管理页面一个按钮手动更新。"
先把**现状实测**写清楚，再说方案——因为两条分发线的能力差别很大：

| 线 | 现在能不能知道"线上是哪一版" | 实测 |
| --- | --- | --- |
| 网页（GitHub Pages） | **不能**。`tools/publish.py --status` 只报本地最新包（包名/提交号/文件数/字节/打包时间），`live_version()` 只发一次 curl 拿 HTTP 码 | 同一地址两次现读分别得到 `code=000` 与一个 GitHub 404 页——这台机到 Pages 的连接本来就抖（`docs/OPS-deploy-domain-2026-10-19.md` 第十一节）。线上包里**没有版本指纹文件**，所以"差多少"无从算起 |
| 小程序（阿里云 OSS 批次 + 指针） | **能，而且不用密钥**。`oss-release.js list/verify` 全是匿名 GET | 本地最近批次 `0ab256f5cf02`（167 个文件）≠ 线上指针 `d25932f1c7a3`（143 个文件）→ 这一行就是"落后了、要不要发"的答案 |
| 板块新旧（两条线共用） | 能 | `scale.json` 的逐板块核对日（7 天提示 / 14 天拦红）+ 每日报告的超期原始快照计数（今天 **11 份 → 0 份**） |

方案分三步，都长在现有件上，不引新依赖、不加常驻服务：

1. **新增 `tools/reconcile.py`（只读，产出一张表）**：逐板块给「本地成品日期与条数 → 本地批次里那份的 SHA-256 →
   线上指针那份的 SHA-256 → 一致 / 变了 / 线上还没有」，末尾两行总线（网页包 vs Pages 指纹、小程序批次 vs 指针）。
   差分口径借 DVC 的 `dvc status -c`：分三类列——**指针里没有的 / 哈希不同的 / 指针有而本地没有的**，按板块分组。
   前置的一小步：发布包里带一份 `version.json`（包名 + 提交号 + 打包时间 + 逐文件哈希摘要），随 dist 一起上线，
   这样网页侧也能回答"线上是哪一版"。**只加一个文件，不改数据、不改门禁、不改页面。**
2. **工作台加一页「对账」**（`tools/admin/` 里加一个只读接口 + 一段表）：三色行借 Dagster 的 freshness policy
   那套表达（这块源已重抓 / 门禁已过 / 已进线上批次），红黄绿的原料现成就有——`daily-report.py` 的步骤表 +
   `data-status.py` 的陈旧度 + 上面那张对账表。每行的「一键刷新」已经有了（现在 9 个板块带按钮）；
   **页尾那个"发布"默认只打印计划（相当于 dry-run），要真发必须再点一次确认**——指针换的是线上玩家当天读到的那一份，
   这一层不做一键直达，也不进 `daily.sh`。
3. **每日报告里顺手贴同一张表**：不打开页面也能看见"本地比线上新多少"。

明确**不抄**的三条（都是这次调研里看过、但撞我们现状的）：
DVC 的"数据移出 git、指针入库"（会让 `build-data.js` 的 provenance 卡口失效，JSON 的可读 diff 也变成黑盒哈希）；
CMS 那套分支/审批草稿流（单人站 + 工作台有意"只本地提交、绝不 push"，开分支等于自己造冲突）；
任何要常驻服务 + 元数据库的编排台（Airflow / Prefect / Dagster / Crawlab / Pimcore）。
另外 `data-diff`、`Static CMS` 已归档，Cloudflare Pages CMS 的仓库与文档现都 404——这三条不能当依据。

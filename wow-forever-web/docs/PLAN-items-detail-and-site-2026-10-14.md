# PLAN · 物品数据落地与站点增强（2026-10-14）

依据：`docs/wow-infinite-sources.md` 第十四节（GearInsight_Forever）与第十五节（XR_DungeonGuide）
的盘点结论；台账挂着的"物品详情二批抓取排期"拍板。角色：wow-data 出条目级采编方案，交站主拍板。

## 0. 先修正一个口径

站内一期名录（21,077 件）**已经有 `ilvl`（装等）与 `rlvl`（需要等级）**——来自 wclbox 名称索引，
"二批缺装等/需要等级"的说法作废。真正的缺口是**详情层字段**：

| 字段 | 站内现状 | GI（beta 解包） | XR（社区整理稿） | wclbox 详情页 |
| --- | --- | --- | --- | --- |
| 属性（+5 精神 等） | ✗ | ✓ `st` | ✓ `st` | 未探明 |
| 卖价 | ✗ | ✗ | ✓ `sell` | 未探明 |
| 来源（哪座本/商人） | ✗ | ✓ `src` | 部分（loot 关联） | 未探明 |
| 英文名 | ✗ | ✓ `nEn` | ✗ | 未探明 |
| 背包格数等杂项 | ✗ | ✗ | ✓ `bp/st` | 未探明 |

## 1. 方案 A（推荐先行）：离线详情落地，零外部请求

**新增 `src/data/items-detail.json`**（独立文件，同 `dungeon-quests.json` 模式：只有详情抽屉
懒加载，不拖累列表页与首屏），由新工具 `tools/merge-items-detail.py` 从两份本地插件拷贝生成：

- 取数字段：属性 `st`、卖价 `sell`、来源 `src`、英文名 `nEn`——**四类全是事实性字段**；
  描述/攻略/评价一律不取。
- 来源层级与冲突规则：**GI（beta 解包转述，L0 档）> XR（社区整理稿，L1/L2 档）**；两源不一致
  时取 GI 并把差异对记进 `meta.conflicts`（不丢信息）；XR 独有的字段标 `srcFrom: "xr"`。
- 每条带 `fetched`（各自文件头日期）与出处声明（写进 `meta`，不在页面铺开——玩家页"缺口集中说"
  原则，溯源页可见即可）。
- 覆盖估算：XR 14,352 ∪ GI 1,515 ≈ **14.5k / 21,077（69%）**；其余 31% 不造假——抽屉里对应
  区块整块不渲染（不摆"待实测"占位铺满）。
- `build-data.js` 加物品详情段校验：id 必须存在于 items.json、不允许出现概率字样、`st` 必须是
  字符串数组、`meta.counts` 守恒。
- 体积预算：估算 1~1.5MB（懒加载可接受；不进 search.json、不进小程序 export）。

## 2. 物品库页增强（ItemsPage.vue，两栈口径）

1. **点行开详情抽屉**（复用副本详情抽屉的交互模式）：全部已有字段 + 新增四类字段 + 每字段
   来源标注（GI/XR 徽标只在抽屉里，列表行不加列不加角标）。
2. **装等区间筛选芯片**（ilvl 数据一期就有，筛选一直没做；与现有"等级区间"并排）。
3. 列表行**不加列、不加角标**（表格已 5 列，375px 已贴边）。
4. `site-check.py` 物品详情断言：抽屉字段与 JSON 一致、无描述文案泄漏、无 `%`/概率字样、
   抽屉懒加载失败时不崩页（显示"这一件的详情还没收录"）。

## 3. wclbox 详情抓取（方案 B，二阶段校准源，不阻塞 A）

- 成本未知（逐件 SSR 页 × 21,077，礼貌间隔 0.5s ≈ 3 小时起步，还有解析成本）。
- 建议先**试采 1 页（200 件）**评估：字段比 GI/XR 多多少、值不值得全量。多不了就不跑，
  A 方案 + 31% 待实测收口；多了再排全量（当周 6h 预算内跑得完就跑）。
- 跑全量的话结果进 `upstream/wclbox-items-detail.json`，merge 工具加第三源，层级最高。

# wow-xxx 角色机制的使用建议

日期：2026-10-22｜主角色：wow-pm｜状态：**已定（诊断与六份 skill 更新）**。2026-10-22 用户明确要求立即更新过时 skill，本文件后半记录已执行修订。

## 判断

**角色 skill 不会提升模型的智力，也不保证文章、方案或代码更好。** 它的主要作用是减少范围漂移、遗漏数据来源、跨端误用和“实现了却没验”的问题。对本项目的数据采编、开发、上线等交付，按一个主角色执行并保留对应验收，通常更容易得到可回查的结果。这里的“通常”是根据本仓库规则与过往交接作出的工作判断，不是做过有/无角色对照实验得出的量化结论。

不用角色或在构思阶段少用角色，可能更容易提出跨领域的新思路；但发散本身不等于方案更好。早期探索最需要的是多提出可能性和反例，最终交付最需要的是选一条路线、查证并验收。因此建议把**发散探索**和**收敛交付**分成两个动作，不用六个角色依次过一遍才能讨论创意。

## 本仓库看到的两类真实问题

1. **角色能防漏，但也会过时。** 根 `AGENTS.md` 明确 2026-10-18 网页可免费分享宏/WA，而 `.trae/skills/wow-pm/SKILL.md` 仍写“两端共同不做宏”；根规则已明确新站是唯一产品，`.trae/skills/wow-dev/SKILL.md` 仍描述 Vue 新站“迁移中”。`wow-data` 的旧 skill 写第三方 BiS 结论一律不取，根规则已为配装名单设限定例外。角色 skill 若不先与根规则和最新用户决定对照，会把旧限制当新结论。冲突时以用户最新指令、根规则和现行原件为准。
2. **角色不能替代理解需求。** 近期我们曾提出“先定玩家问题”、还规划资料站新页面；用户实际上要求先从素材库找线索，随后明确不新增资料站。即使按角色产出文件，仍可能在理解顺序与范围上犯错。质量关键是及时回读用户原话、核对现状，并在发现偏差时修订上游文件。

## 建议的轻量用法

- **提想法时：** 指定一个主角色即可（通常 `wow-pm` 或 `wow-planner`），明确允许提出多种路径、反例和非本职的启发；这一步只遵守最新硬边界，不让旧模板预先决定答案。角色是最终归档责任，不是思考围栏。
- **选方案时：** 回到用户目标、真实素材/代码/数据和成本，淘汰没有证据的想法。只让最相关的下一角色接手，不默认串六角。
- **要落地时：** 数据由 `wow-data` 核源，代码由 `wow-dev` 验证，页面由 `wow-ui` 留渲染证据，发布节奏由 `wow-ops` 核对；主角色每轮一个，跨角色按文件交接。可不写冗长模板，但必须留下关键决定、证据、未验项和验收结果。
- **读 skill 时：** 先以根 `AGENTS.md`、目标子项目规则、最新用户决策和实际文件复核；把过期条目当待修文档，不当现行禁令。对只需简短判断的任务，用简短产出和一行台账即可，避免角色仪式吃掉思考时间。

目前没有做“同一任务用角色/不用角色”的盲测，不应声称质量差异有固定幅度。若想验证，可挑三类相同难度的小任务（选题、页面、代码修复）做对照，事前约定评分：新意、事实错误、返工次数、完成时间与可验证性；最终由站主盲评。未经对照前，最稳妥的选择是**发散阶段放松角色话术，交付阶段保留责任和验收**。

# BiS 线两问：数据怎么保持更新 · 3D 人物能不能做（2026-10-26 实测）

本轮角色 wow-data。只查与量，不改界面、不动红线。参考站 = `wowforever.wclbox.com`（新手盒子）。

## 0. 三句话结论

1. **BiS 数据现在没有任何"保持更新"的机制**：纯手工抓、上次是 10-22、没有任何一处会告诉你它旧了，页面上给的还是第二份（插件）的日期。
2. **3D 人物那条路，参考站的做法已经完全看清**：不是热链查看器，是**每个配装方案离线烘成一个 GLB**（平均 284 KB，全站只有 12 个），前端懒加载 three.js 渲染，默认先给一张同模型的静态图当降级面。
3. **我们能不能照做：方案本身能照做，但卡在一个没验的前置上**——玩家装备→模型文件的映射表（`ItemDisplayInfo` / `CharSections` / `PlayerKit` 这一类）本服客户端里到底有没有，我们一次都没导过；这个探针必须在站主那台 Windows 上跑一次才能判生死。

## 1. 「保持 BiS 数据更新」现在的真实状态

**链路**（全手工两步）：

```
tools/scrape-wclbox-bis.py   真浏览器，38 页；联盟读 SSR，点 .pz-faction 的「部落」再读一遍
        ↓ app/data/upstream/wclbox-bis.json   meta.scrapedAt = 抓取当天
tools/merge-bis.py           与第二份名单合并 → app/data/bis.json（38 套 / 177 件 / 6,670 备选行）
tools/extract-addon-bis.py   第二份：XR_DungeonGuide/Data_Bis.lua（钉 sha256 前 16 位）
```

**节奏**：`tools/refresh.sh` 里有 `bis` 分支，但要人跑；`crontab` 没有本仓库任何条目；唯一的 launchd 是 `tools/com.wowforever.nga-daily.plist`（NGA 热帖线，跟 bis 无关）。`docs/DATA-MAINTENANCE.md` 全文没有 bis 这一节。

**现值**：`bis.json.meta.scrapedAt = 2026-10-22`（今天 10-26，已经 4 天），`meta.alt.fetched = 2026-10-23`。

**四个真问题**（不是"建议改进"，是会直接导致说假话的那种）：

| # | 问题 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 没有任何一处比较 `scrapedAt` 与当天 | `build-data.js` 只校验格式与 ID 存在性 | 名单在参考站改了，我们不会知道，页面继续用四天前的口径 |
| 2 | 页面上只显示**第二份**（插件）的日期，主源哪天抓的不给看 | `app/src/pages/BisPage.vue:142` 只读 `meta.alt.fetched` | 玩家看到的"更新到 10-23"其实是插件那份，主源是 10-22 |
| 3 | 门禁把日期抄成了字面量 | `tools/site-check.py:1816` 要求对照表里出现字符串 `2026-10-23` | 换日期时它会红，但红的原因是"断言抄死了旧事实"，不是数据错——这是本站第 N 次踩"把会变的数写进不会变的地方" |
| 4 | BiS 没进"逐板块版本表" | `build-data.js` 的 `SECTION_CN` 名单里没有 `bis.json`（它的日期键叫 `scrapedAt`，不在 `VER_KEYS` 里） | 溯源页那张逐板块表看不到配装这块是哪天核的 |

**本轮实测差分**（今天 09:43 用现成脚本重抓 38 页，与库里 10-22 那份逐套逐格比）：

| 比什么 | 结果 |
| --- | --- |
| 38 套的套名 / 等级段 / URL | **0 处不同** |
| 每套两套阵营的纸娃娃主选件（16 格 × 2 × 38） | **0 处不同** |
| 两套阵营全部备选行（**7,779 条**，含顺序） | 条数相等、内容 **0 处不同** |
| 附魔串（如「力量 +5」） | **0 处不同** |
| 来源指向 `refs`（配方 / 任务 / 副本链接拆出来的那层） | **0 处不同** |

结论：**10-22 那份到今天仍然是准的，参考站这四天没动过配装名单**。核对日已刷进库
（`upstream/wclbox-bis.json` 与 `bis.json` 的 `scrapedAt` / 逐套 `fetched` → 2026-10-26，
内容零变化），`build-data.js` rc=0、`site-check --only bis` **40/40**。
——但请注意：**这次"没变"是运气，不是机制**。上面那四个问题一个都没解决，
下次它改了，我们照样要等到有人手动跑一遍才知道。

## 2. 保持更新的方案（分层，都要站主点头才做）

- **A. 过期可见（最小、纯本站，建议先做）**：`build-data.js` 加一条"主源 `scrapedAt` 距今 > N 天就提示 / > M 天就红"，并把 `scrapedAt` 加进 `VER_KEYS` + `SECTION_CN`，让 BiS 出现在溯源页那张逐板块表里；`BisPage` 把主源日期显示出来。N/M 由站主定（建议 7 / 14 天）。
- **B. 拆掉抄死的日期**：`site-check.py:1816` 那条改成"从 `bis.json.meta` 现读日期再比"，不留字面量。
- **C. 定时重抓 + 差分报告**：照 NGA 那条 launchd 的同构做法，每天跑一次 scrape 到带日期快照，与上一份逐套比，输出"哪套哪件换了/多了/少了"的清单；**无变化就只更新核对日，不改成品**。风险：对方页面改版会静默少抓——现有脚本已经卡"38 套 / 每套 16 格"，改版会红，这条判据要保留并加"格子总数对平"。
- **D. 差分要不要自动进成品**：建议**不要**——名单是 L1（一家资料站列过），自动覆盖等于让别人的排序改动悄悄变成我们的结论。C 只出报告，改不改由 wow-data 看一眼再落。

## 3. 参考站的 3D 人物是怎么做的（逐条实测证据）

今天在他站上抓的，全部可复算：

| 观察 | 实测值 |
| --- | --- |
| 默认视图**不是 3D** | `<img class="pz-poster" src="/moxing/bis/ecaaaacee165.webp" width="340" height="470" alt="推荐配装角色预览">` + `<button class="pz-3d" aria-pressed="false">旋转 3D 模型</button>` |
| 点下去才加载 3D | 新增 12 条请求：`assets/three-zpdom5lB.js`（584,277 B，canvas 上标 `data-engine="three.js r180"`）+ `assets/GearModel-DoWQ15Sf.js`（1,711 B）+ `moxing/bis/ecaaaacee165.glb`（**306,648 B**，`content-type: model/gltf-binary`）+ 9 个 `blob:` （Draco / KTX2 解码 worker） |
| 图片是降级面不是装饰 | 点完按钮文案翻成「返回图片」，`aria-pressed="true"`，容器加 `data-live="true"` |
| 规模很小 | 9 个职业页去重只有 **12 个模型**（部分职业两档各一个）；抽样 6 个平均 **284 KB**；整站 3D 约 **3.4 MB** |
| 不做单件预览 | 物品页 `/wupin/19019` 里 `glb` 命中 **0** —— 只做"配装方案"这一层，不碰 21,421 件 |
| 背后有自动重烘管线 | 那个 `.glb` 的 `last-modified: Mon, 26 Oct 2026 01:02:54 GMT`（**今天凌晨**），文件名是 12 位内容哈希，`cache-control: public, max-age=3600, s-maxage=86400` |

**一句话**：每个配装方案**离线烘成一个 GLB**（身体 + 该套装备合并成静态姿势，纹理压 KTX2、网格 Draco），前端 three.js 只负责把它转起来；默认给静态图，点一下才下载模型。**不是**运行时按物品 ID 拼模型，**也不是**热链 wowhead/wow.tools 那类在线查看器。

## 4. 我们能不能用同一方案：三道门槛，两道没验

### 门槛①「模型文件拿不拿得到」——**没验，但路铺了一半**

- 已证明的：`wowfexport get <安装根> wowf id <FileDataID> <目录> <名> <日志>` 能按号从 CASC 里取二进制（图标线 160 张 `.blp`→PNG 就是这么来的，第二轮还把它判死到 EKey 级）；导出方在包内 `RESULT.json` 的 notes 里确认 `CreatureModelData.f2 = 模型 .m2 的 FileDataID`。
- **卡点**：玩家装备走的是另一套表（`ItemDisplayInfo` / `CharSections` / `PlayerKit` 这一类）。这三张表**本服客户端里有没有、列是什么，我们一次都没导过**——本地那份导出包只有 12 张 DB2（`.scratch/wow/ziliao-export-2026-10-22/db2/`：AreaTable / Creature / CreatureDisplayInfo / CreatureModelData / Faction / Item / ItemSparse / LoadingScreens / ManifestInterfaceItemIcon / Map / QuestInfo / Spell），全仓 grep 这三个名字 **0 命中**。
- 所以第一个探针必须在站主那台 Windows 上跑：按现成流程把这三张表导一次，判"表在不在、能不能拿到装备的 .m2 号"，再随手取一个 `.m2` 落盘（判二进制能不能取）。**这一步不做，后面全是空谈。**
- 一条已知限制不影响这件事：DB2 文本是韩文卡的是"名字层"，模型文件与语言无关；listfile 缺失卡的是底图链，`wowfexport ... id <fdid>` 这条路不需要文件名。

### 门槛②「m2 → GLB 有没有转换器」——**有，但不是命令行**

- `Kruithne/wow.export`（Marlamin 那套导出工具的 node-webkit 移植）README 明写：支持 Retail 与 Classic、**"Export models as OBJ, GLTF and more"**、可拖本地 M2/BLP 转换、带 Blender 插件；官方只出 Windows 构建。
- 代价：它是 **GUI，没有 CLI** → 38 套要能重烘，只能"批量拖 + 人工"，做不到参考站那种"名单一变自动重烘"。要自动化得自己写脚本走它的内核，那是另一笔工时。
- 另一条路（前端直接渲 `.mdx`，wow-models 那一类）意味着把游戏原始模型文件按运行时装进浏览器，体积与合规都更难看——**没实测过，先不当方案**。

### 门槛③「红线让不让」——**要站主拍板，我不能自己改**

现在的红线是：素材一律本地留存、禁止热链；客户端原画（2D 画面类）允许经第三方站转存，但要独立目录 + manifest 记来源与抓取日期 + 整目录删除即回退。**角色 3D 模型比原画硬一档**：那是可运行的游戏资产，不是画面截图。三条要你先定：

1. 允不允许把游戏 `.m2` 烘成 GLB 放进我们的静态托管（GitHub Pages）？
2. 允许的话，只做"配装方案"这一层（12–38 个文件、几 MB），还是也要物品单件预览（2 万量级，我直接建议否）？
3. 界面口径要不要照他们那样"默认静态图、点开才 3D"？（我倾向照做：省流量、没有 WebGL 也能看、和现在的职业原画不冲突。）

**明确不许做的两件事**：热链他的 `/moxing/*.glb`（红线禁止热链第三方域名）；把他的 GLB 下载下来当我们自己的资产（那是他烘焙的衍生资产，不是客户端原文件，也不在我们那条"客户端原画经第三方转存"的例外里）。

## 5. 成本与回退

- **前端**：three.js 分包约 584 KB（未压缩）+ 一个 1.7 KB 组件，**必须懒加载**（点开才要），首屏不受影响。这是我们站**第一个 3D 依赖**（现在 `package.json` 与源码里 three/glb/gltf 零命中）。
- **素材**：按 284 KB/套估，38 套 ≈ **11 MB**，加海报图再 1–2 MB。静态托管可接受；**小程序那条线不做**（主包预算与"素材不进主包"的规则）。
- **登记**：照现有那套 manifest 走（`app/img/models/manifest.json`，字段 `file/bytes/sha1/source/kind/fetchedAt` + `origin: client-export`），`fetch-art.py`/`app-assets.py` 按 manifest 重算的规矩不变。
- **回退**：删 `app/img/models/` 整个目录 + 去掉那个按钮，就回到现在的 2D 纸娃娃（`BisPage.vue:53` 那句"本站没有 3D 素材"改成历史说明）。

> 剩下的仍是这两件：#103 那次 Windows 探针（决定真模型有没有）、#104 红线拍板（决定能不能上静态托管）。

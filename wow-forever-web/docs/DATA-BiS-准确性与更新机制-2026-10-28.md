# BiS 数据准确性与更新机制 · 2026-10-28

本轮角色：wow-data ｜任务：回答 BiS 推荐名单怎样保持可信、怎样及时发现和发布变化 ｜产出：本文件 ｜交接给：wow-dev。

## 1. 先定义能保证什么

BiS 的“哪件更好”是社区推荐，本站没有模拟计算或游戏内实测，**无法保证推荐强度客观正确**。本站能保证的是：① 逐格忠实记录所标来源；② 名单指向的物品事实与当前基底一致；③ 来源一变会在约定时限内发现并进入审核；④ 线上版本能追溯到审核过的快照。两份社区名单可能共享上游，不因“相同”就自动升 L0。维持根规则的 L1 和固定声明，不复制推荐理由、权重、掉率或循环建议。

**“实时”分三段**：发现来源变化 → 审核差分 → 发布到 GitHub Pages。静态站不能自动保证与第三方站同一秒更新；能承诺的应是可度量的发现与发布时限。客户端 build 号、名单核对时间、名单内容变化时间、本站上线时间分别记录，不共用一个“更新时间”。

## 2. 当前链路与缺口

主名单：新手盒子 `https://wowforever.wclbox.com/peizhuang` → `tools/scrape-wclbox-bis.py`（真浏览器，联盟 SSR + 点击部落）→ `app/data/upstream/wclbox-bis.json` → `tools/merge-bis.py` → `app/data/bis.json` → 网页 / 小程序导出。第二份是 XR 插件 `Data_Bis.lua`，只并列展示；最新版 XR 87 的文件哈希与 10-23 快照相同。装备名称、装等、属性与出处来自 `items.json`、`items-detail.json`，不从名单重复抄。

本地原成品是 **38 套、9 职业、1,261 个两阵营纸娃娃格**，主源核对日 **2026-10-26**；截至 2026-10-28 为 2 天。与 XR 的第二份名单对照，1,237 个有对照的格位中 **917 格不同**；差异不等于某一家错，但足以说明“有第二源”不能替代推荐审核。现有 `build-data.js` 已在核对日超过 **7 天提示、14 天拦截新构建**，并要求名单 ID 在物品名录、来源 URL 与日期齐全、分级 L1、无掉率百分比。此闸能拦陈旧或结构错误，**不能发现来源站在核对日之后改了什么，也不能评价推荐强度**。线上 GitHub Pages 不会因为本机构建红了而自动下架旧包。

下列缺口会造成“刷新成功但仍抓漏”：

1. `scrape-wclbox-bis.py` 在没找到部落按钮时仍写 `horde: null`；`merge-bis.py` 会跳过这侧，`build-data.js` 只要求联盟非空。必须要求每套两阵营均有已完成切换的证据；两边物品可以相同，但不能以“点击失败”充作“相同”。
2. `build-data.js` 只要求套数不少于 30，而现有路由表是 38 套；漏抓 1–8 套仍可能放行。刷新前从配装总览发现当前套装集合，与抓取结果严格对账；新增套装进入待审，不可悄悄忽略。固定 38 只能作为当前基线，不能永久钉死。
3. `tools/refresh.sh bis` 与 8830 管理台当前“更新数据”按钮会直接重写主快照和成品并跑门禁，没有“只检查、给出差分、审核后应用”的隔离步骤。即使门禁通过，来源站改了首选件也会静默进入本地成品；它不会自动部署线上。
4. 当前过期闸只看 BiS 自己的 `scrapedAt`。插件或物品属性更新后，即使 BiS 名单文件未变，页面展示的同一件装备事实也可能改变；需要依赖项复核。2026-10-27 逐文件复核见 `DATA-插件更新来源复核-2026-10-27.md`。
5. `scrape-wclbox-bis.py --out-dir <新目录>` 不会建立目标目录。本轮第一次临时重抓读完 38 页后在写文件时报 `FileNotFoundError`（rc=1），未产出快照；建目录后重跑。自动化前应先建候选目录，并用原子写入避免半套快照。

## 3. 建议的日常更新协议

| 触发 | 频率与承诺 | 动作 | 结果 |
| --- | --- | --- | --- |
| 日常完整巡检 | 每天一次，建议北京时间 08:00；来源变化最迟约 24 小时发现 | 38 套及总览发现到的新增套装全部抓到候选目录；不触碰 `app/data` | `checkedAt`、成功/失败、逐格语义差分、源版本与 SHA-256 |
| 客户端 build / 官方阶段变化 | 发现后当天加跑完整巡检 | 先核来源是否跟上新 build；即使名单未变，也复核当前等级段与物品可用性 | 标“来源仍为旧 build”或生成待审变更 |
| 物品、技能、专业或掉落来源更新 | 对受影响的 BiS 物品 ID 立即复核 | 查 ID 存在、部位、等级、阵营、装备限制、属性、出处；推荐排序不自动改 | 受影响套装清单与审核状态 |
| 来源站不可达/页面改版 | 当次巡检判失败并通知维护者 | 保留最后一次**完整**核对日与已审核成品，不改时间戳；超过阈值按既有过期闸处理 | 失败原因、最早失败时间、重试结果 |

临近正式上线或重大补丁，可临时增加轻量 build 探测；只有 build 变化或日常巡检到点才完整抓 38 页。全量抓取需要真浏览器，不应每分钟跑。**每天巡检不等于每天发版**：无语义变化只更新“核对日”的审核记录；有变化需核完再发布。成本主要是本机 Chrome 跑约 38 页、审核差分与一次静态站部署；不需要新付费服务，耗时按实际运行日志累计。

## 4. 候选与审核规则

**候选快照与线上真源分开**。候选按抓取时间存到管理台待审目录，原始快照保留 URL、抓取日、源页面标示的 build、每套/每阵营完整性、每页响应结果和整份 SHA-256。比较时剔除抓取时间，只按语义键 `(职业, 专精, 模式, 等级段, 阵营, 部位, 格位, 备选顺序, 物品 ID)` 生成差分；附魔、消耗品和 `refs` 另列。输出“新增/移除套装、首选替换、备选顺序变化、链接变化”，每条带旧值、新值与源 URL。

**机器拒绝条件**：任一目标页失败、来源总览与抓取路由不一致、缺任一阵营、格位/备选缺失、重复套装 ID、物品 ID 不在名录、已知部位或装备限制冲突、已知 `items.json.rlvl` 高于套装等级段、来源 URL/日期缺失、正文或掉率字段混入、合并前后条数不守恒。没有可核字段时列“待人工核”，不把空值当通过。现有门禁继续保留，并补上述未覆盖项。合法阵营差异不要求两边相同。

**人工审核条件**：任何主选件、排名顺序或新增/删除套装；物品事实变更导致推荐可用性变化；两份名单分歧扩大；来源页面声明的 build 改变。审核人至少核源页面对应格、本站物品 ID/属性与来源、等级段和阵营约束；没有可核实证据就标“待核”，不猜一件替代品。审核可以决定“同步来源名单”或“维持已发布版并注明旧核对日”，但不能悄悄按多数票选强度。游戏内实测或独立证据若有，逐格留截图/时间/版本，仍须按项目分级规则处理。

**应用与发布**：审核通过后才更新 `upstream/wclbox-bis.json` 与 `bis.json`，记录候选哈希、差分摘要、审核人和审核日；运行 `node tools/build-data.js`、小程序 `node tools/export-mini.js`、网页构建与 `site-check` 的 BiS 段。打包后核线上 `bis.json` 哈希与本次已审核产物一致，并核页上来源日期。小程序需要单独走 OSS 批次发布，网页更新不会自动同步小程序。保留上一版包与快照，异常可回滚。

## 5. 给 8830 管理台和页面的最小改动单（交 wow-dev）

1. 将 BiS 的单个“更新数据”流程拆为 **“检查更新”→“查看逐格差分”→“应用已审核候选”**。第一个按钮只写待审目录；第二个显示套装、阵营、部位、旧/新物品 ID 与源链接；第三个才执行合并与门禁。不得在抓取成功前先改成品，也不得以“总数没变”判定无变化。
2. 补全量与部落侧强断言，以及来源总览路由发现；用夹具证明“缺 1 套”“少部落侧”“点了按钮但仍读联盟”“新增套装”“同套只换备选顺序”均能被发现。
3. 每日巡检只在结果变化、失败或超过 7/14 天时提醒；不让无变化通知淹没待审差分。显示四个独立时间：**来源标示的客户端 build、最近完整核对、最近名单内容变更、本站最近发布**。失联时保留上次真实核对日。
4. 给 BiS 增加依赖复核：`items.json`、`items-detail.json` 或相关插件快照变更时，列出受影响的在榜 item ID 与套装；不能只凭 `bis.json` 没变就宣告页面准确。

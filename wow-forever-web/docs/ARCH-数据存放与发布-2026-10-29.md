# 数据放哪、怎么发出去（2026-10-29 站主批准的做法）

问句原话：**"web 到时候会部署到域名，那这些数据怎么储存、储存到哪，这些数据也需要被小程序使用，
写公众号有些专业名称图标也会参考这里的数据。不可能一直提交上传。怎么弄方便呢？"**

## 一、结论四句

1. **真源继续放 git**（`wow-forever-web/app/data/`），不换数据库、不换网盘、不换"改一次传一次 OSS"。
2. **提交 ≠ 发布**。提交已经自动化了（刷新链跑前自动收口、跑完自动提交产物，见
   `DATA-MAINTENANCE.md` 第九节），它秒级完成、不需要人动手；**发布才是对外动作，只有你点头才做一次**。
3. **三个消费者三条出口**，不要都去读 git（见下表）。
4. 发布只有一个入口：**`python3 tools/publish.py`**。

## 二、现状：谁读什么

| 消费者 | 读的东西 | 走哪条路 | 需要网络上传吗 |
| --- | --- | --- | --- |
| 网页（资料站） | 构建产物 `app/dist` 里的静态 JSON | 现在 `publish.py --target web` → GitHub Pages；**备案号下来后换成阿里云 OSS/FC，同一命令换个 provider** | 只在发布那一次 |
| 小程序 | 同一份 `app/data` 导出的批次 | `publish.py --target mini` → `export-mini.js` + `oss-release.js` 的**批次 + 指针清单**，客户端只读指针 | 换数据不用发版，只换指针 |
| 公众号 / 写稿查名称与图标 | 直接读本机 `app/data` | 同机器读文件，零成本 | 不需要 |

**玩家读的是打包出来的文件，不是 git。** 所以"部署到域名"这件事不改变数据存放方式，
只改变产物放在哪台机器上——**不需要后端，也不需要数据库**（`backend/` 那条线仍未建，也不急着建）。

## 三、为什么不用别的东西存

git 在这里同时给四样东西，换存储就得四样重建：

| git 给的 | 换成数据库/OSS 之后 |
| --- | --- |
| 门禁：`build-data.js` 校验、`audit-translations.py` 逐字回查、`site-check.py` 635 项 | 要另做一套"改完能验"的机制 |
| 溯源：每条数据带来源 URL + 核对日期，改错了能 diff 出是哪一次改的 | 数据库里改一次就覆盖，**没有"上一版长什么样"** |
| 回退：一句 `git revert` 退回上一个数据提交 | 要自己留快照 |
| 并发：多个会话同时写，冲突在提交时暴露 | 变成"谁后写谁覆盖"，正是这次刷新链要避免的事 |

而且"玩家信这条数据"靠的正是前三样——**能说出这条是哪天从哪一页核的**，是这条线的产品本身。

## 四、发布这一侧现在长什么样

```bash
python3 tools/publish.py --status                      # 本地是哪一版、线上通不通、数据最久没核的是哪块
python3 tools/publish.py --target web --dry-run        # 只打印会跑什么
python3 tools/publish.py --target web                  # 门禁 → 打包 → 验收，不上传
python3 tools/publish.py --target web --push           # 真发布（对外动作）
python3 tools/publish.py --target mini --env beta --upload
```

三条硬规矩写在脚本头部：**不加 `--push`/`--upload` 什么都不上传**；
**`app/data`/`app/img` 有未提交改动就拒绝打包**（要越过得显式 `--allow-dirty`）；
**这个脚本从不 push 源码仓**——源码提交与推送永远是人的动作。
每次执行往 `docs/PUBLISH-LOG.md` 追加一行（时间、目标、包名、对应提交、结果）。

它只做编排，**不重新实现任何一步**：门禁调 `refresh.sh publish`，打包调 `release-package.py`，
验收调 `pkg-verify.py`，上传调 `deploy-gh-pages.py` / `oss-release.js`。

## 五、已知接缝（现在没堵的，别当已解决）

1. **`-dirty` 有两套判据**：`release-package.py` 看**整仓**未提交改动，`publish.py` 只看**数据目录**。
   多会话并发时别人的未提交文档也会把包名标成 `-dirty`——所以 `publish.py` 不拿包名当拦路石，
   但会打一行提醒并把"包带 -dirty 标记"留在发布台账里，**不静默放行**。
2. **`--target web` 的上传目标还是 GitHub Pages。** 换成阿里云要等备案号，且要先答一个问题
   （已记在 `OPS-icp-filing-2026-10-22.md` 第 8 节）：**函数计算那张门票是否要求域名必须解析到函数计算本身**。
   答案决定 provider 写 OSS 还是 FC，**现在不预先实现**。
3. **`--status` 里"线上"那句只作参考**：这台机到 Pages 的连接本来就抖（吞吐实测见
   `OPS-deploy-domain-2026-10-19.md` 第十一节），读不到不等于线上下线。
4. **mini 那条依赖 OSS 凭证**，且 `oss-release.js` 的默认 bucket 是 `poe2-all-class`（PoE 那条线的）——
   本站只允许写 `wow/{env}/v1/` 那一段，脚本会打印实际 bucket 与前缀，不许静默复用别线仓。
5. **截图留存规矩从没执行过**：`docs/screenshots/` 里 10 个 `check-*` 批次都在库里、
   `screenshots-archive/` 一个 tar.gz 都没有（见 10-29 台账）。仓库体积一直在涨，
   真要治有两刀：按规矩归档截图批次，或把 `app/data/upstream/`（22 MB，最大那份 items-detail 7.7 MB）
   挪出主仓只留成品 JSON——**后者代价是丢掉上游快照的逐条 diff**，不建议现在做。

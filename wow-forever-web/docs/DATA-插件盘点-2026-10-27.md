## 三、OpenMap 手里到底有什么

它不是"一张更大的地图图片包"。它把一个我们**自己判死过的问题**解开了：
**无限服客户端里没有 `MapArea` / `MapDiff` / `TextureData` 这三张表**（2026-10-22 我们逐张查过，
`maps/resolve.csv` 里那 9 行 `ok=false` 就是这个结论），所以我们拿不到"哪个本哪一层 = 哪 12 个贴图文件号"。
OpenMap 的 `Data/DungeonMaps.lua` 头注释写了它的来路：**UiMap 表取自正式服 5.5.4.70268、层与分区名取自正式服
日志 12.1.5.70391、文件取自无限服安装**。它绕开了无限服缺表这一格。

它带的数据表（`Data/*.lua`，24 张）与实测计数：

| 表 | 内容 | 本轮实测数 |
| --- | --- | --- |
| `DungeonMaps.lua` | **25 座本 / 63 层**官方副本图，每层 12 个贴图文件号；51 层带层名、15 层带分区（wing）标注 | 756 个文件号，**在自家 listfile 里 756/756 命中且 `name_kind=verified`**（逐号回读，非抽样） |
| `Caves.lua` | 39 座洞穴 / 进本前那片小图，带**世界坐标框**（minX..maxY，码为单位）+ 12 个文件号 | 39 条 |
| `Places.lua` | 副本与团本**入口在世界坐标上的位置**（27 条）、没有入口的 4 条、29 张 mapID 的**首领名单（游戏内顺序）**、25 条交通（船/飞艇/飞艇岛）、12 段航线轨迹 | 见左 |
| `Levels.lua` | 42 个区域的等级区间。**手工录入**，出处写在文件头：warcraft.wiki.gg 的 "Zones by level (original)" | 42 条 |
| `Fishing.lua` | 43 个区域的钓鱼基础技能。**手工录入**，出处 cMaNGOS classic-db 的 `skill_fishing_base_level` | 43 条 |
| `Minimap.lua` / `MinimapLOD.lua` | 小地图瓦片 → 文件号 1,724 条，与逐级缩小的合并片 | 1,724 |
| `Reveal.lua` | 按 `UiMapArtID` 索引的"探索过/没探索过"分片文件号 | 键是 UiMapArtID，正是我们缺的那一层 |
| `ZoneArt.lua` / `Gaps.lua` / `Grade.lua` / `Labels.lua` / `Banners.lua` | 无缝世界拼接用的瓦片表、色匹配乘数、**地名是活的不是烘在图上的**（含每条名的笔画坐标） | — |
| `NameCN.lua` | 汉化分支加的**人译中文名 353 条**（副本层名 + 首领名），明确写"只用于显示，数据层仍是游戏英文名" | 353 条 |

素材侧：`Media/Textures/` 32 个子目录、约 283 MB。其中 `MapArt/`（世界 + 两大陆，**手涂掉原有地名**）、
`MapMiniLOD/`、`MapDungeonDrawn/` 是 256² 24-bit **TGA**（我们现有那条 TGA 链能直接读）；
`MapZones/`（224 片 512²）是 **BLP/DXT5**——**本机没有任何 BLP 解码器**，这一格我没打开看，不猜。

## 四、逐格判定：能不能完善地图

| 我们的缺口 | OpenMap 有没有 | 判定 |
| --- | --- | --- |
| **副本内部底图只有 28/30 座**（缺达拉然城、奥妮克希亚） | 奥妮克希亚的**官方图**在 `DungeonMaps.lua` [249]（12 片，listfile 全命中）；达拉然那 4 座游戏内**本来就没有图** | **能补 1 座**（奥妮克希亚），另 3 座仍然只能自绘或继续留数字 |
| **首领点位只有一张图、层号只写在浮层里**（第五节那条） | 63 层逐层官方图 + 层名 + 分区 | **能补，这是它最大的价值** |
| **8 个区域没有底图**（1424 希尔斯布莱德、1430 逆风小径、1440 灰谷、1449 安戈洛、1451 希利苏斯、1453 暴风城、1457 达纳苏斯、2548 河林） | 它的 `MapZones/` 有全部区域的图，但那是**从英文客户端烘出来的**，区域名大概率还烘在图上（它只承诺涂掉了世界/大陆的"卡利姆多""无尽之海"那类大字） | **先不用**。我们现在这 37 张是**带中文地名**的（实测 `1413.webp` 上有"莫高雷""千针石林"），换它等于从中文地名换成英文地名，风格反而倒退。要判死它得先有 BLP 解码器打开一片看 |
| 世界 / 大陆总览图 | `MapArt/` 947 + 1414 + 1415 各 12 片 256² TGA，**地名已手涂掉**（本轮拼出来亲眼看过：整幅零文字） | **可用**，且是我们没有的一种东西：一张能自己排中文名的干净底图。代价同第五节的许可判断 |
| 洞穴 / 进本前那片小图 | 39 座，带世界坐标框 | **全新的一格**，我们目前完全没有这一层 |
| 航线与交通 | 25 条交通 + 12 段轨迹（另有 xeR 插件那份按区域图的飞行点百分比） | **全新的一格**；`world.json` 的 zones 里已经有 `flight` / `flightNote` 两个字段在等这类数 |
| 区域等级区间 | 42 条，手工表带出处 | 我们那格已按 2026-10-13 拍板定稿（wclbox 卡片为准），**这份只作对照，不覆盖** |
| 首领中文名 | 353 条人译名 | 按红线"两源分歧两个都留 + 标注来源"进对照，**不许升 L0、不许当官方译名** |

一句话：**OpenMap 对我们最值钱的不是它那 283 MB 图，是那 756 个文件号和那张"哪层是哪 12 片"的表**——
图我们本来就能自己从客户端导（10-21 那条路已经跑通），缺的一直是"该导哪些号"。

## 五、许可与红线的三条边界（动它之前先读这段）

1. **MIT 只覆盖它的代码与数据表**。`LICENSES/README.txt` 原文分得很清：
   "OpenMap's own code and data tables: MIT … **Textures cut from Blizzard's map art: see ../Media/Textures/NOTICE.md**"，
   而 NOTICE 第一句是 "Every texture here is either cut from World of Warcraft's own map art
   (**Blizzard Entertainment's, not covered by OpenMap's MIT licence**), generated from noise, or … drawn by a player"。
   → 我们**取 fdid 清单（MIT 的数据表），不取它的 .blp/.tga**。图自己从客户端导，
   按 AGENTS.md「客户端原画」那一格走：独立目录 + `manifest.json` 记来源与抓取日期 + 整目录删除即回退。
   这条同时避开"禁止热链第三方素材"。
2. **画师 Santiago Reyes 的自绘副本图与海图不能拿**。NOTICE 明写那两目录
   （`MapDungeonDrawn/` 4 座：达拉然城 / 湿地挖掘场 / 洛丹伦废墟 / 领主大厅，`MapChart/` 那一圈海图）
   "not covered by OpenMap's MIT licence"，授权是给 OpenMap 用的。
   → 我们那 3 座 addon-drawn 示意图**继续用 XR 那份**（站主 2026-10-19 已单独拍板），不去碰 Reyes 的。
3. **署名义务**：MIT 要求保留版权声明。取它的数据表就要在溯源页那条来源里写
   `OpenMap 0.7.5-CN（MIT，作者 jiforever 与 OpenMap contributors；上游发布页 curseforge.com/wow/addons/openmap）+ 抓取日期 2026-10-27`。
   顺带一条它 README 里的事实：**原作者 GitHub 账号与仓库已下线（404）**，公开镜像停在 v0.4.0-beta——
   也就是说这份数据**没有可回查的上游代码**，只有 CurseForge 发布页。按我们"每条带 url + 抓取日期"的口径，
   url 只能填发布页。

## 六、顺手量出来的一条我们自己的毛病（要修，不是 OpenMap 的问题）

**首领点位画错了参照物**：一座本的多层坐标被画在同一张图上。

- 我们的成品里 `bossPos` 每颗点带 `floor`（例：影牙城堡出现层号 2 / 6 / 7，通灵学院 2 / 3 / 4，
  血色四翼分别是 1 / 2 / 3 / 4），**30 座里有 15 座带层号、7 座的点跨多层**。
- 这层坐标的来路是 DungeonsForever 的 `Data_MapPins.lua`，它的第 4 个元素就是层号，
  而 DF 自己的渲染 `Core/MapUI.lua:574 ExtraPinsFor(id, floor)` 是**按层过滤**的——
  它每次只画当前那一层的点，底图也是切给那一层的那张官方图（`MapUI.lua:233` 直接引 `Interface\WorldMap\`）。
  → 这证明**这套百分比坐标的定义域是"某一层的那张官方图"**。
- 我们这边 `DungeonPage.vue:373 bossMapItems` 把所有层的点一律画到 `bossMap` 那**一张** XR 图上；
  而那张图实测是 **512×512 的等轴"12 个房间摊平"合成图**（本轮打开 `dmap_shadowfangkeep.webp` 看过：
  立体渲染 + 手写的 1–12 房间号 + 箭头，不是游戏里那张 1002×668 的平面分层图）。
  两种参照物不是同一个坐标系。
- 所以：**同一只首领那颗点落在合成图的哪个房间，是未经验证的**。层号我们印在浮层里，点的位置却没有按层走。
  这条属于"界面说了假话"那一类，不是精度问题。
- 修法就是第四节那一格：按 `DungeonMaps.lua` 的 63 层导出官方逐层图，**一层一张、只画那一层的点**，
  层名用它的（51 层有名，配 `NameCN.lua` 的人译名对照）。顺带把 XR 那 24 张合成图退成"总览"用途或干脆不用。
  成本：756 片 256² BLP（原始约 33 MB，转 webp 后按我们现在这套估计 2–4 MB），Windows 侧一条批量导出脚本。

**没取的那几样，写清楚为什么**：
`Data_DungeonRates`（掉落概率）——红线"掉落不写百分比"，10-22 那份资料包清单里也已经明写不导；
BagSync / BagBrother / Bagnonium——它们带的是**每个角色的背包与银行内容**（BagSync 自述"追踪你所有角色的物品"），
撞"战绩类玩家数据一律排除"那条，不碰；
`163UI_Info`——网易DD 自己的分发元数据，不是游戏数据；
XR 的 `Data_QuestDB.lua`（4.9 MB 全地图任务）——**不是不能取，是范围问题**：我们现在只有"本里的任务"，
要不要开"全地图任务"这一整块得站主与 wow-pm 先定，本轮不动。

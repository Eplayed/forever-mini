## 补记 · 日更链全红修复（2026-11-03 当日）

**现象**：站主从 00 屏真跑日更链，探源①绿，其后所有重抓步全红：
`tools/refresh.sh: line 33: set: pipefail: invalid option name`（rc=2）。

**根因**：本机 `git core.autocrlf=true`，`tools/refresh.sh` 工作树是 **CRLF** 行尾（221 行全是），
WSL bash（本机 `bash` = `C:\Windows\System32\bash.exe`，内部 GNU bash 5.2）把
`set -euo pipefail` 读成 `pipefail\r` → 选项名非法。`daily.sh` 本身是 LF，所以链上纯 python 的探源步是绿的。
同样中招的还有 `tools/nga-daily.sh`、`tools/serve.sh`、`tools/taskboard/install.sh`。

**修复**：
1. 四个 .sh 工作树转 LF；
2. 新增 `wow-forever-web/.gitattributes` 钉 `*.sh text eol=lf`（连带 `*.py` `*.js`），谁 checkout 都不再变 CRLF。

**验证**：`bash tools/refresh.sh __repro_noop__` 报错消失（打印 usage、exit 2 符合预期，不碰任何数据）；
`bash -n` 四个脚本全过；panel 上重新跑链即应归绿（链本身一步没改）。


## 补记 · 第二轮真跑 8 红的三个 WSL 环境缺口（2026-11-03 当日）

**现象**：CRLF 修复后站主再跑日更链（steps.tsv 13:52），①探源、③official/items/spells/achievements/icons、
④并成品、⑥对账、⑦报告 9 步绿（动了 74 个数据文件），但 8 步红，根因收敛为三个环境缺口：

| 缺口 | 红掉的步骤 | 根因 |
| --- | --- | --- |
| A. WSL 无 node | ③world/changes/prof/legacy + ⑤门禁（5 步 rc=127 `node: command not found`） | 本机 `bash`=System32\bash.exe=WSL；node 只装在 Windows 侧 `C:\Program Files\nodejs`，WSL 查找不认裸 `node` |
| B. WSL python3 无 playwright | ③dungeons/talents/quests（`ModuleNotFoundError: No module named 'playwright'`） | WSL 侧 python3 连 pip 都没有 |
| C. 插件路径只有 Windows 形式 | ②插件层抽取（`找不到 C:/GAME/...`） | `addons_root.py` 候选表没有 `/mnt/c` 视角 |

**修复与验证**：

1. **缺口 A**：`wsl -u root` 建 `/usr/local/bin/node` wrapper（`exec "/mnt/c/Program Files/nodejs/node.exe" "$@"`），
   验证 `node -v` = v24.13.0；`node tools/build-data.js` 在 WSL 下完整跑通 **rc=0「校验通过」**
   （此前一次中途 rc=1 未复现，判定为当时 ④ 合并未跑完的中间态，非稳定问题）。
2. **缺口 B**：apt 装 `python3-pip` → 清华镜像装 playwright 1.64.1（直连 PyPI 卡死 12 分钟零进度，换镜像后秒下）→
   npmmirror 下 chromium headless shell 156.0.8078.4 → `playwright install-deps chromium` 补系统库
   （首启报 `libnspr4.so` 缺失）→ 自检 `chromium launch: OK`。
   配套：`browser_channel.py` 已加 Linux 无系统 Chrome 时回退 `pw.chromium.launch()`（不带 channel），
   banner 如实显示「playwright 自带 chromium（WSL 回退）」。
3. **缺口 C**：`addons_root.py` 的 CANDIDATES 与 EXPORT_CANDIDATES 各加两条 `/mnt/c/GAME/...`，
   实测命中 `_cn_beta_/Interface/AddOns` 与 `ziliao-export`；Windows 侧 `os.path.isdir` 对 `/mnt/c` 恒假，自动跳过，两边互不干扰。

**过程教训（照实记）**：WSL 后台 `nohup` 安装任务两次被"虚拟机重启"带走（`wsl` 会话断开后 VM 存活期极短，
`uptime` 实测 0 min）——长安装必须同步在单个 `wsl` 会话里跑完；一次性探针脚本（probe-node/verify-bridge/
setup-wsl-bridge/setup-wsl-py/probe-fix-status/probe-pip/probe-chromium）已清理，
修复命令以本补记为准。

## 补记 · 第三轮「点了没反应」（2026-11-03 当日，紧接上一节）

**现象**：站主再点 00 屏「跑今天的日更链」，无任何反应，steps.tsv 停在 13:52 旧轮。

**根因**（两层）：
1. **服务端**：面板 server.py 是 13:07 在某个终端窗口里起的，那个终端后来被关掉，进程成孤儿仍活着——
   此时它 spawn 的 `bash.exe`（WSL 启动器）拿不到可用控制台，直接 **rc=3221225794（0xC0000142，DLL 初始化失败）**，
   daily.sh 一步没跑、steps.tsv 纹丝不动。同机同参数从活终端 spawn 一切正常（实测 rc=0），坐实是父控制台问题。
2. **观感**：失败写进 00 屏「本次操作」卡，但链格子不动，站主看到的就是"点了没反应"。

**修复**：
1. `jobs.py::_stream_run` 的 Popen 加 `CREATE_NO_WINDOW`（Windows 专项：子进程自带隐藏控制台，
   不依赖父进程控制台死活）+ `stdin=DEVNULL`；Linux 无此常量按 os.name 跳过。
2. 面板服务重启（`Start-Process -WindowStyle Hidden`，从此不挂在任何终端上，孤儿问题不再产生）。
3. 修复后本人经白名单 POST 真发一轮日更链（jobId fb41b9e2f849）：
   ①探源 / ②插件层抽取 / ③world / ③changes 依次 rc=0——**上一节三个环境缺口的修复被真链逐格验证**
   （② 的 /mnt/c 路径、③ 的 node 桥都是上轮红的步骤）。全链跑完以 steps.tsv 与当日报告为准。

**给下一轮**：面板服务如果再出现"点了没反应"，先看 00 屏「本次操作」卡里的报错，
rc 形如 322122xxxx 的是 Windows 进程层没起来（不是链红），重启面板服务即可。
